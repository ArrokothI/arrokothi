# Operational and communication terms

Three loose families of vocabulary sit alongside the [core coordination terms](core.md), naming pieces of the physical and interpersonal world the protocol itself is deliberately silent about. **Where code runs and what it may touch** — [Kernel Worker](#kernel-worker) and [Execution Host](#execution-host), the two trust modes, and the [operating profile](#operating-profile-and-durability) that says what a deployment actually tests for. **Time** — the [three clocks](#three-clocks) that answer three different questions about an Execution and must never share one timer. **Executions talking to each other and to observers** — [children](#child-and-ownership), [messages](#message-request-and-correlation), [cursors](#observation-cursor-and-routing), and the [debt](#backpressure-and-cleanup-debt) that accumulates when observers or cleanup fall behind.

Each term is defined here and used elsewhere. This page says what the pieces are; [communication](../mechanisms/communication.md) and [output](../mechanisms/output.md) own how they behave together, [deployment](../deployment.md) summarizes the first family, and [resources](../mechanisms/resources.md) owns the physical cost of any of them. The page assumes the [core vocabulary](core.md) and the weekly-report Execution introduced there.

## A first example

The weekly-report application runs as a web backend. Inside its long-lived OS process live a [Kernel](core.md#kernel), the storage where the report Execution's [progress](state.md#progress) is kept, and the Node.js code the report's [Runtime](core.md#execution-runtime) is written in. A separate small helper process runs the publication step in a sandbox with no filesystem access and no outbound network except to one approved API, so a maliciously crafted draft cannot walk out with the store's contents or reach the internet at will.

That one paragraph touches every family this page names. The web-backend process holds two roles at once: it is a **Kernel Worker**, because it advances the Kernel's accepted records, and an **Execution Host**, because it runs Runtime code. The web-backend process runs Trusted, because it intentionally holds ambient credentials and file access; the publication helper runs Isolated, because a tested sandbox physically restricts what its code can reach. The deployment's **operating profile** promises that a process crash is survived because the storage the Kernel writes to survives, and it promises nothing about destroyed disks, other data centers, or hostile co-tenants.

Meanwhile the report is waiting for its editor for at most a week, the Execution as a whole must finish within a month, and whichever worker is currently advancing it holds that claim for a minute at a time — three time bounds that answer three different questions and would be nonsense to fold into one field. The report spawns a helper Execution to gather the week's figures, and owes an answer for that helper before it can complete. It sends a review-request message to a peer Execution owned by the copy-editor. After the report is `COMPLETED`, an operator dashboard is still reading its accepted output, and a delivery adapter is still trying to email the report out. The rest of the page picks up each term in the order the paragraph above touched them.

## Kernel Worker

A **Kernel Worker** is a role: whichever code, in whichever OS process, is running the Kernel's transitions right now — accepting an [Outcome](core.md#outcome), minting a [timeout Event](core.md#timeout-event), advancing a [readiness](core.md#readiness) record. It is not a required standalone service. In the web-backend example the same process that answers HTTP requests is also the Kernel Worker, because the code that authenticates a request and the code that commits an accepted decision live in one binary. In a larger deployment the role can be pulled out into a separate service pool; that is a deployment choice, not a promotion of the role into a new kind of thing.

Naming the role at all matters for one specific reason: when a process dies, the questions "did an accepted decision survive?" and "did the work someone was doing survive?" have different answers, and both are legitimate. The first is answered by [recovery](../mechanisms/recovery.md) reading what a persistent store still holds. The second is answered by whatever the [Driver](core.md#execution-driver) can prove about a native session. Kernel Worker names the actor of the first question so that the second stays a separate topic — and both stay separate from any claim that anything was prevented from crashing at all.

## Execution Host

An **Execution Host** is the process role that runs Runtime code — the Node.js runtime, a Python interpreter, a job pod running a native agent framework, whatever the [Definition](core.md#definition) actually requires to execute. It is again a role, not a required separate deployment unit: one process can hold both this role and the Kernel Worker role, and in the embedded web-backend example one process does.

Two Execution Hosts running the same Runtime code do not thereby serve the same Execution. Which Execution a Host is currently advancing is decided by an authorized [dispatch](identity.md#dispatch-and-delivery); which Runtime an Execution uses is pinned by its [Runtime contract revision](identity.md#revision). The Host is where the code physically runs, not an identity for the work.

The reason for keeping this role named separately from Kernel Worker is failure independence. A Runtime can outlive a Kernel Worker — a long native job may keep running on its Host after the Kernel process it was talking to died. A Kernel Worker can outlive its Runtime — a Host process holding a native agent can crash while its Kernel keeps quietly accepting decisions on other Executions. A deployment that folds both into "one server" cannot even talk about these two failure modes, let alone test for them; [independent failures](../deployment.md#independent-failures-and-resource-costs) owns what a deployment does about them.

## Trusted Execution

**Trusted Execution** means the Runtime is intentionally allowed to touch the ambient host — its filesystem, its network, its subprocesses, the credentials the process itself is authenticated with. Nothing exotic is going on here; this is the normal case for a piece of code running in a normal environment. The web-backend's own Runtime is Trusted, because it holds the database credentials that let it commit progress and read the operator's UI tokens, and there is no reason to pretend those credentials are somehow physically out of its reach.

The point of naming Trusted at all is to make the choice visible. A Runtime that is Trusted may take ambient actions the Kernel never sees. The Kernel's [authority checks](../mechanisms/authority.md) apply only to work that comes to it through a [mediated path](actions.md#exposure-and-mediation): the Runtime asking to publish, the Runtime asking to create a child, the Runtime submitting a message. A Runtime running Trusted that decides to write to `/tmp` and shell out to `curl` never asks the Kernel for permission, because the Kernel is not standing between the Runtime and the operating system. Telemetry can record that it happened, but recording is not preventing. Any deployment that wants unmediated calls to not happen has to physically stop them from happening — which is what Isolated Execution is for.

## Isolated Execution

**Isolated Execution** means the Runtime is physically contained under a tested threat model. The publication helper in the running example runs Isolated: its sandbox has no filesystem outside a scratch directory, no outbound network except to one approved API, and no way to hold long-lived credentials. Isolation is a claim about what code physically cannot reach — enforced by a container, a VM, a browser sandbox, a WASM boundary, something concrete — and the claim is only as good as the tests behind it.

A label is not a claim. Naming a container image `"isolated"` establishes nothing. A profile that says an Execution runs Isolated has to say **against what threat model, backed by which tests**: what happens if the Runtime tries to read another Execution's workspace, follow a symlink out, resolve a private-network address, spawn a subprocess to bypass its own limits, keep going after cancellation. [Containment claims](../mechanisms/resources.md#containment-claims) owns the list.

The single most useful thing to know about Isolation is that it is orthogonal to Kernel mediation, in both directions. A well-isolated Runtime can still make an unmediated call to whatever its sandbox does allow through: an approved outbound API is by definition inside its physical reach, so if the Runtime calls it without going through a Kernel [Effect](actions.md#effect), the Kernel does not know. And a well-mediated Runtime can run with no isolation at all: every one of its mediated actions goes through admission and settlement, and its unmediated ones still touch anything the process can touch. Isolation controls what a Runtime can physically reach. Mediation controls whether the Kernel is on the path when it reaches something. They are separate guarantees, they are established by separate mechanisms, and each is a defect if it is silently used to argue for the other.

## Operating profile and durability

An **operating profile** — sometimes called a support profile — is the concrete claim a deployment publishes about what it has been built and tested for. It states which versions of storage, Runtime and host are covered, which failures it recovers from and which it does not, which limits it enforces, and how long records are retained. It is written down, not implied, because every other page on the site defers questions like "does this survive a crash?" and "what happens under load?" to the profile that answers them for a specific deployment.

**Durable** means, precisely: the specified facts survive the specified failures for the promised period. Nothing more general is intended. A profile that says accepted [progress](state.md#progress) survives a process crash for at least 30 days is durable against that failure mode for that horizon, and durable against nothing else. Extending the word beyond that quickly becomes a lie; the honest form of the promise is always "which fact, against which failure, for how long".

The first persistent profile the architecture describes covers a single administrative domain with process failure and surviving storage — the web-backend case above. Its promise is that a coordinator crash is survived because the store is still there afterward. Its silence is deliberate about everything else: a destroyed disk is not covered, geographic failover across data centers is not covered, safety when mutually distrusting tenants share one deployment is not covered. Every one of those is a larger commitment that has to be built and tested for on its own; naming them here so they are not accidentally implied is the point of writing the profile down at all. [Deployment](../deployment.md) owns which profile a deployment actually holds itself to.

## Three clocks

Three different questions about an Execution have a time limit, and each is answered by its own clock. Different purposes, different expiries, different consequences of expiry. Sharing one timer across two of them would answer both questions with one number, and neither answer would be right.

| Clock | Question it answers | What expiry means |
|---|---|---|
| Wait deadline | How long is this specific [wait](core.md#wait-subscription-and-generation) willing to sit? | End that wait; carry a [timeout Event](core.md#timeout-event) in the next batch |
| Execution deadline | How long may the whole Execution live? | Enter ordered [cancellation](../mechanisms/lifecycle.md#cancellation-order) |
| Scheduler lease | How long may one worker's exclusive claim to advance this Execution stand? | Make the Execution eligible for [recovery](../mechanisms/recovery.md) inspection and reassignment |

Read the report example against each row. The report's wait for the editor's approval has a wait deadline of a week: if seven days go by with no reply, that wait ends and the next Activation carries a Kernel-minted timeout Event so the Runtime learns why it was woken. The report's Execution deadline is a month: no matter which specific waits are outstanding, once a month has passed the whole Execution enters cancellation. The report's current worker's scheduler lease is a minute: whichever host is currently allowed to write for this Execution renews that permission every minute so that a silent host is noticed quickly enough to be replaced.

Folding two of them into one timer is where this section's teeth are. Imagine one universal "timeout" set to a minute so the lease stays fresh — every wait for the editor would fire every minute, and the Runtime would be woken over and over about something that has not actually happened. Imagine instead one universal timeout set to a week to accommodate the editor — a dead worker's exclusive claim would stand for a week, and no other worker could take over. Neither number is correct because there is no single question these two clocks answer at once.

Two more distinctions are worth stating outright. **A scheduler lease is not proof the previous process died.** It expires because time passed, which is equally consistent with a dead worker and a slow one still writing; expiry makes reassignment *eligible*, and [recovery](../mechanisms/recovery.md#decide-permission-before-replacing-work) still has to establish separately that continuation is safe. **A wait deadline is not proof an external action failed.** It ends one wait registration; whether the publication service actually did or did not do what was asked is answered by [action evidence](../mechanisms/actions.md), not by a clock at all.

## Child and ownership

A **child** is another [Execution](core.md#execution) that this Execution asked the Kernel to create. It has its own ID, its own progress, its own authority binding, and its own lifecycle — an independent lifetime addressed by the Kernel exactly as any other Execution is. What binds it to its parent is not shared state but a relationship the Kernel records: this parent asked for this child, under this delegated authority, and expects to account for its result.

**Ownership** is that recorded relationship, and its content is narrower than the English word suggests. Ownership is responsibility for required work — an obligation the parent still has to account for — and not universal access to what the child is doing. A parent does not read a child's mailbox, does not steer its progress, and does not automatically hear about its output. The report Execution spawning a `gather-figures` child does not thereby learn what queries the child is running; it learns whatever the child sends back through mediated paths, and it stays on the hook for whatever it declared as required.

Required work stays required until one of three things happens to it: the parent accounts for the child's terminal result, the responsibility is transferred to a named durable owner who explicitly accepts it, or an explicit decision to abandon the work is recorded under policy. Ending the parent Execution by itself does none of these. A [terminal](../mechanisms/lifecycle.md) parent still leaves a live child under whatever supervision the application defined, and a [cleanup debt](#backpressure-and-cleanup-debt) row for whatever work is unaccounted for.

Four verbs travel with this vocabulary and mean slightly different things. **Call** combines child creation with an immediate wait for the child's required terminal result; it is the safe default when the parent cannot proceed without the answer. **Spawn** omits the immediate wait — the parent creates the child and moves on — but omits *waiting*, not *responsibility*: the child is still owed. **Detachment** is the explicit transfer of that responsibility to a different durable owner willing to accept it; the minimum operating profile may refuse detachment because "somebody else will handle it" is easy to say and hard to enforce. **Supervision** is the application's rule for what happens to a child that fails, gets cancelled, or asks to retry — a policy declared at creation, not an automatic ancestry rule that the Kernel invents.

The one inference the Kernel refuses to draw is that ancestry means permission. A parent is responsible for its child. It is not therefore allowed to do anything the child can do, or to see anything the child sees. [Authority](../mechanisms/authority.md), not lineage, decides what either of them may reach; [communication](../mechanisms/communication.md#children) owns how a child is created, how its terminal result is routed, and what a parent has to account for before it may complete.

## Message, request and correlation

A **message** is input one Execution sends to another. A parent creates its child; a peer merely already exists, so sending to one cannot make it exist and cannot decide what it is currently waiting for. The report Execution sending a review-request to the copy-editor's Execution is a message: the sender authorizes the destination, the Kernel accepts the intent and records a routing obligation, and eventually the message lands in the destination's [mailbox](core.md#mailbox) — or it does not.

"Landed in the mailbox" is exactly what **send success** means, and it is worth stating outright: the message reached the mailbox and was accepted there, and nothing more. It does not mean the destination has read the message, decided anything about it, or intends to reply. Whether the destination wakes at all depends on what it is waiting for; a message sitting in a mailbox with no matching wait is inert. Delivery and attention are different achievements — that the message is in the mailbox says nothing about whether attention will be paid.

Some messages ask for an answer, and that shape has its own record. A **request/reply record** is what the Kernel writes when a message declares that a reply is expected: the sender, the destination, the specific request, and enough context that a later message can be recognized as the reply to *this* one. A **correlation ID** is the label that lets that recognition happen — a name attached to a request so a peer's answer can be routed back to the wait that is expecting it.

Correlation IDs are addressing information, and this section's most important negative sentence is about them: knowing a correlation ID is not permission to reply and not permission to settle. An unrelated Execution that has somehow learned the ID cannot answer for the peer that was actually asked, and the Kernel will refuse a reply from any sender not authenticated as an authorized responder. A **reply** is an observation — a fact the Kernel accepts about what somebody said — and never on its own a [consent](actions.md#exact-consent) to the underlying action, or [settlement](actions.md#settlement-and-reconciliation) evidence about what actually happened in the world.

A **human input request** deserves its own name because it looks like a message and behaves nothing like one. Human answer times are measured in wall-clock hours and days rather than seconds, and any assumption a service peer holds by default — that the same OS process will still be around when the reply lands, that showing the question and creating it are the same event, that the reply channel is the same channel the request went out on — fails on people. So the term names a durable object with one owner rather than a synchronous callback: the object is created together with the wait that depends on it, and rendered from that one record as many times as the interface needs. [Communication](../mechanisms/communication.md#human-input-requests) owns the mechanics; the term is here so that "human request", "human message" and "human reply" all point at the same object rather than at three subtly different ones.

## Observation, cursor and routing

An **observation** is a read of something the Kernel has accepted — the current progress, retained output, an accepted Emission, the History of decisions on an Execution. The operator dashboard reading the report's output is doing an observation. So is another Execution reading a governed value it has been authorized to see. Reading changes nothing about what is being read: an observation acknowledges no Event, wakes no wait, and moves no cursor except its own — [observation does not send input](../mechanisms/output.md#observation-does-not-send-input) owns the rule in full.

A **cursor** is a position in a stream of retained output for a specific [view](roles.md#view-and-disclosure) of an Execution. If the operator dashboard disconnects and reconnects, its cursor is what lets it pick back up where it left off without missing an accepted Emission or repeating one. The word "cursor" is chosen deliberately for its narrowness. A cursor is a position, and that is all. It is not authority — reconnecting is authorized afresh against current policy, not on the strength of the cursor — and it is not a subscription that the Kernel is pushing to; the reader still has to ask, or an application-owned notifier still has to tell it, that new output has been accepted.

A **routing obligation** is a duty the Kernel accepted to deliver a specific piece of information later. A child's terminal result routed back to its parent is one; a request/reply routed back to the requester is another; a delivery adapter's promise to ship an accepted output out to an email address is a third. Each is an obligation to *arrive somewhere*, and each is fulfilled by the destination actually accepting the delivery — not by the source finishing its work. A child terminating creates a routing obligation to the parent; the parent's wait for the child's result is only satisfied when the destination Event exists in the parent's mailbox, not when the source obligation was recorded. [Ending a wait](../mechanisms/waits.md#ending-a-wait) owns that ordering.

## Backpressure and cleanup debt

Two things pile up in systems whose fast parts do not match the pace of their slow parts, and both have names here because both have a way of being counted in numbers that hide who owns them.

**Backpressure** is what the slow side exerts on the fast side to keep the fast side from producing more than the slow side can absorb. In the report example, a slow operator dashboard consuming accepted output cannot indefinitely make the Kernel keep every Emission ever produced: that would let a single slow reader pin every Execution's history in memory forever. The rule that resolves this is that a slow consumer either uses bounded buffers or disconnects with a resumable cursor and an explicit gap — never an empty-looking successful read that silently hides missed content. And if the Kernel is asked to accept an [Outcome](core.md#outcome) whose promised output cannot fit in retained storage under the current profile's limits, the honest response is to refuse or hold that acceptance *before* commit — the alternative would be an accepted record whose promise the Kernel already knows it cannot keep. [Slow consumers](../mechanisms/output.md#bounded-retention) owns the mechanism.

**Cleanup debt** is the running total of work that has been started, or resources that have been allocated, but has not yet been terminally accounted for. A retention window that has not yet expired is debt; a delivery attempt that is still `unknown` is debt; a workspace that a completed Execution held open is debt until it is explicitly released. The point of naming it as a running total is that it does not vanish when an Execution enters a terminal state. `COMPLETED` says nothing about whether an emailed delivery finally landed; `CANCELLED` says nothing about whether a native job on some remote host has stopped; `FAILED` says nothing about who is going to pay the storage bill for the retained History. Every one of those obligations still has an owner after the lifecycle line has been crossed, and it stays owed until whoever owns it does something about it. [Capacity, cancellation and retention](../mechanisms/resources.md#capacity-cancellation-and-retention) owns the accounting.

The habit of thought this section is trying to install is small but load-bearing: an Execution reaching a terminal state is a fact about accepted records, not a claim that the world has cleaned itself up. The records say the Execution is done. The debt column says what is still owed. Anyone reading either without the other is looking at half the answer.
