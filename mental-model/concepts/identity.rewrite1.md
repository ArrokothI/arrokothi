# Identity, attempts and accepted versions

A coordination protocol earns its keep in the moments when timing stops being polite. A caller's request disappears into silence, so the caller sends it again. A host goes quiet mid-task and a replacement is authorized — and then the original host comes back to life, work in hand, and reports as if nothing happened. Identical content arrives twice from one producer, and once each from two producers who mean different things by it. None of these arrivals can be understood from its own contents. Each can only be understood by comparison against decisions the [Kernel](core.md#kernel) has already accepted, and a comparison has to know which question it is answering before it can answer one.

The terms on this page supply those questions. Each identity below exists to settle one exact form of *the same as what?*, within one named **scope** and under one **equality rule** — because equal content is almost never the right rule, and the wrong scope is how a system duplicates work it meant to do once, or loses work it believed was safe. The sections follow the life of one [Execution](core.md#execution) through the five kinds of sameness it will meet:

- **Requests from a caller** — the [request key, Input ID and creation key](#request-key-and-input-id), which tell a retry of an old intention apart from a new one.
- **Efforts at one exchange** — the [Activation ID and Runtime attempt](#runtime-attempt), and the [writer epoch](#writer-epoch), which keep one question distinct from the successive efforts to answer it, and decide which effort may commit.
- **Sends** — [dispatch and delivery](#dispatch-and-delivery), which keep "the Kernel recorded its intent" from being confused with "bytes arrived somewhere," and both of those from being confused with acceptance.
- **Accepted states** — the several kinds of [revision](#revision), which say which version of a named value a decision was made against.
- **What an acceptance covers** — [acceptance, boundary and receipt](#acceptance-boundary-and-receipt), which fix exactly what a returned proof does and does not establish.

Two conventions hold across the whole page. These names are conceptual: they fix what must be distinguishable, and what decides sameness, never how an API, a wire format or a storage schema spells them. And the weekly report introduced by the [core vocabulary](core.md#a-first-example) runs through every section, so the cast of characters never changes.

## A first example

An application wants its weekly report prepared. It sends a create request carrying a key the application chose itself, `report-w38`. Somewhere between the two of them the reply is lost. The application does what every caller does after a silence: it sends the same request again, under the same key. When the dust settles, exactly one Execution exists, and the second call was answered with the record of the first call's decision. The key — not the content — is what allowed "again" to mean *the same request*, because the content could just as well have been a second report that someone genuinely wanted.

The Kernel now prepares the report's first exchange. It pins the accepted [progress](state.md#progress) the work starts from, fixes the [batch](core.md#batch-reservation-and-acknowledgment) of [Events](core.md#event) the exchange will carry, records all of that *before sending anything*, and only then hands the [Activation](core.md#activation) to the [Driver](core.md#execution-driver). Two identities are already at work doing different jobs. The Activation ID names the question being asked. The writer epoch — 1, here — names which working attempt may answer it.

Mid-draft, the host goes quiet. Its scheduler lease expires, which proves that time passed and nothing more: the host may be dead, or slow, or seconds from finishing. [Recovery](state.md#recovery-and-re-execution) eventually establishes that the native work can safely be taken over, and a replacement attempt is authorized. The question does not change — same Activation ID, same pinned input. The epoch advances to 2.

Then the original host resurfaces, draft in hand, and submits a perfectly respectable [Outcome](core.md#outcome). The Kernel rejects all of it. Not because the draft is wrong, and not because the Activation ID names a dead question — that ID still names exactly the exchange that is open, and that is what makes the rejection illuminating: the draft's content is irrelevant next to the one label that decides, and the epoch this host carries no longer may commit. Had the takeover instead minted a *new* Activation ID, an earlier shape of this design, the same late answer would have been refused for naming a question that never closed — a false account of events. The question was alive the whole time. Only the right to answer it had moved.

Attempt 2 finishes the draft. The Kernel accepts its Outcome, installing progress revision 1, and returns a receipt for that acceptance. The receipt settles exactly one question — this proposal was accepted, at this boundary, at this position — and settles nothing the proposal merely requested. Had the Outcome asked for the report to be published, the request would now exist as an accepted obligation; whether anything was ever published is a different question, answered by different evidence.

Five kinds of identity each played a part in that story, and confusing any two of them rewrites it into a worse one. The sections below take them in order.

## Request key and Input ID

A **request key** is a caller-chosen identifier that the caller reuses when it retries one intended request. `report-w38` is one. Caller-chosen, and reused on retry: those two properties are the entire mechanism. A caller whose answer never arrived can ask again without risking a second report, and a caller who genuinely wants a second report can say so — by choosing a different key.

What the key is not is a content hash, and resisting that optimization is the one judgment this term exists to protect. Hashing the payload would spare the caller any cooperation, which is exactly why it fails: two intentional requests may carry byte-identical content — the same report ordered twice, the same payment made twice on purpose — and content equality cannot tell those from a retry, because the distinction lives in the caller's intent and only the caller can express it. Content equality is not discarded, though; it is put to the opposite use. When a key is reused, the remembered content of the original request is compared with the new one. Same key and same content answers from the already-recorded decision. Same key and different content is a conflict — the key claims sameness and the content contradicts it — and the second request creates nothing. Different keys with identical content are simply two requests.

An **Input ID** is the identity under which duplicate detection for later input actually runs: the triple *authenticated producer namespace, destination Execution ID, producer request key*. Each component rules out one collision the other two cannot. Two unrelated tenants may both send input keyed `17`, and neither should see the other's trace of that key. One producer may send `17` to two different Executions, and those are two different inputs. Only the third component is caller-supplied text; the first two come from the system's own records.

The namespace in particular is taken from trusted principal context established at ingress — never from a field inside the payload. A `user_id` that a payload writes about itself is content, and content [is not authority](../mechanisms/authority.md#content-is-not-authority): if a producer could name its own namespace, it could choose another producer's, and then replay, shadow or deliberately conflict with that producer's inputs by writing the other name into a message. Scoped this way by construction, an Input ID is a duplicate-detection identity for one producer's traffic, not a deduplication service shared across unrelated callers.

A **caller-scoped creation key** applies the same logic one step earlier, at the moment when no Execution ID can be part of the identity because nothing exists yet. The authenticated caller scope plus the caller's request key identify one create request, and the identity binds the complete creation content — which is what lets a retried creation carrying changed content be recognized as a conflict rather than silently applied as an update. This is a scope rule. It introduces no new durable object type and fixes no token format.

Creation and later input are **separate identity domains**, and the separation repays a walk through the failure it prevents. Accepting the initial input during creation does not consume a post-creation Input ID: the initial Event keeps its creation provenance and its creation receipt, and a later ordinary input from the same producer may reuse the creation key's text as a fresh ingress request. Suppose the domains were merged — creation spending the producer's later-input key space. An ordinary input under the key the producer chose at creation would then be answered with a *creation* receipt for an ingress it never performed: the wrong question, answered confidently. Worse, genuinely new content under that key would be permanently refused as a conflicting duplicate of a request the producer never made, because creation had already spent the key. [Later input has a destination](../mechanisms/creation.md#later-input-has-a-destination) owns the ingress rules this separation makes possible, with the reuse case worked through.

One identity that shows up all over this page lives elsewhere by right. The Execution ID — the name of one logical lifetime, never reissued — is defined with [Execution](core.md#execution), and its never-reused rule is what lets every identity on this page assume that a destination names at most one piece of work, ever.

## Runtime attempt

An **Activation ID** names one immutable semantic exchange — the pinned progress revision, the fixed Event batch and the input that [Activation](core.md#activation) defines — for as long as that exchange remains unresolved. It answers *which question is this*. The Kernel mints a new one only when a genuinely new exchange begins: after the previous exchange has resolved and a fresh dispatch is prepared.

A **Runtime attempt** is the currently authorized effort to perform one unresolved exchange, and it answers a different question: *whose work is this*. The two identities are separate because one question can outlive the effort made against it. Redelivering the same dispatch — because the first send may never have arrived — continues the same attempt; nothing about who is working has been re-decided. An **authorized takeover** is the only decision that replaces the effort, and what it produces is a second attempt at the very same exchange — a Runtime attempt is not replaced by a new question, and a new question is not disguised as more work on the old attempt.

Keeping the two identities apart is what makes a late answer classifiable. Three situations look identical from outside — once more, the Kernel is trying to get this work done — and they differ in nothing except which identity survived: ordinary redelivery preserves both, takeover preserves the exchange and replaces the effort, a new exchange after resolution preserves neither. [Retry versus takeover](../mechanisms/execution-cycle.md#retry-versus-takeover) sets the three side by side. An implementation that merges the identities cannot say what a reconnecting host's Outcome means: an answer to the live question, a ghost of a superseded one, or a stranger's work? It has to pick a story, and every wrong story either double-counts work or quietly discards it.

A **physical action attempt** — one invocation of a mediated action through a trusted adapter — borrows the word *attempt* for a different concept with a different owner, defined under [admission](actions.md#admission-and-physical-action-attempt). The two are not nested sizes of one idea. A Runtime attempt is an effort to answer the Kernel's question; a physical action attempt is an effort to change something in the world. They fail for unrelated reasons and are fenced by unrelated counters, so where both are in scope, **attempt** never appears unqualified.

## Writer epoch

A **writer epoch** identifies which Runtime attempt's Outcome may be accepted for the current exchange. It increases monotonically — an integer, or any equivalent total order — within that one exchange. An authenticated takeover decision advances it. Nothing else does, and redelivering an existing dispatch in particular does not, because redelivery re-decides nothing about who is at work.

The epoch fences **the whole of an Outcome acceptance**, and the list of what that covers is the point: batch acknowledgment, progress, emissions, Effect intents, the registered wait and its deadline, readiness, and the next lifecycle state. Fencing only the progress would produce an accepted record that describes a decision no single attempt ever made — the replacement attempt owning the saved continuation, while the fenced-out attempt's acknowledgments, output and action requests pass underneath it and commit anyway. One accepted record is always one attempt's whole proposal, or nothing at all; [Outcome acceptance](../mechanisms/execution-cycle.md#outcome-acceptance) owns the atomic step that enforces it.

The epoch resembles three things it is not. It is **not authentication**: trusted ingress settles who is calling before the epoch question is even asked — the epoch ranks attempts, it does not identify callers. It is **not liveness**: a host answering the network proves nothing, and a scheduler lease expiring proves nothing; the authoritative record decides, not whichever machine is currently talking. And it is **not a lock on anything physical** — not on a native session, not on a filesystem, not on shared state another Execution also touches. A fenced-out attempt may keep running native code for hours and keep mutating a native session the whole time; what it cannot do is make any of that accepted. Single-writer acceptance fences whose report becomes truth, which is a narrower claim than concurrency control — [shared mutation](../mechanisms/resources.md#shared-mutation) is a real problem with its own owner, and the epoch is not its solution.

Two representation questions are deliberately open, and one of them comes with a cautionary tale. How an epoch is spelled — integer, fencing token, opaque counter — is an implementation choice. So is whether the sequence resets or continues when a genuinely new Activation begins, and a conformance fixture once demanded a literal comparison of epoch values across new Activation IDs: under that reading, no implementation could pass unless it happened to share the fixture's accidental convention, even though every one of them behaved correctly. The only behavior the architecture actually requires is rejecting a stale epoch for the *current* exchange; an implementation owes no one a particular sequence of numbers. (The K1.1 in-memory coordinator happens to number each exchange's epochs from 1. That is its choice, not a protocol fact.)

Two nearby words are easy to mistake for this one. **Attempt epoch** is the writer epoch's former name; these pages use *writer epoch* everywhere, and the old name should stay retired, because a reader who meets both will reasonably assume two mechanisms. An **attempt envelope** is the transport wrapper that carries attempt metadata around the immutable exchange — a container, not a second epoch, not an identity, not a recovery mechanism. Takeover replaces what the envelope carries while leaving the exchange's pinned input untouched, which is precisely what keeps the Activation ID honest across it.

## Dispatch and delivery

**Activation dispatch** is the Kernel preparing one Activation and sending it through a Driver toward a Runtime. It is neither [creation](../mechanisms/creation.md#one-atomic-creation) nor a selection of which Runtime implements the work — both of those were settled before the exchange existed.

A dispatch's **dispatch intent** is the accepted record that fixes, before anything is sent, the exchange's input, its reserved batch and its current attempt. The order — record first, send second — is the design, and the reason is a crash window. A Kernel that sent first and recorded afterwards could die in between, leaving a Runtime at work on an exchange the survivors cannot reconstruct: which Events were handed over, from which pinned progress, as which attempt? Neither safe redelivery of the same question nor a safe new question is possible when no one can say what was asked. With the intent accepted first, a restart instead finds a pinned exchange it can redeliver unchanged. [Before sending](../mechanisms/execution-cycle.md#before-sending) owns exactly what gets pinned.

**Delivery** is an ordinary transport verb, and the only rule this page makes about it is a naming rule: always say what was delivered, and to whom. The discipline pays because the two everyday hops may be physically nothing alike — "Activation handed to the Driver" can be a function call inside one process, while "Driver submission to the native runtime" may cross a network to a job API — and because the logical route Kernel → Driver → Runtime promises no two physical hops at all. What neither hop can ever mean is acceptance. Bytes arriving somewhere is a property of a transport; acceptance is a decision of the Kernel. Receipt of bytes at either hop is not Outcome acceptance.

Between send and answer the Kernel wants exactly one fact — *did the hand-off reach the Runtime* — and it is reported explicitly, through a reporting capability the Kernel supplies alongside the Activation, rather than read out of whatever the dispatching call happened to return. [The delivery reporting boundary](../mechanisms/execution-cycle.md#delivery-reporting-boundary) owns the whole rule: the first report about an attempt stands, a report changes no accepted state, and a late report settles only the retained attempt it describes.

Three other operations in this architecture are also, in plain English, dispatches and deliveries, and each has its own owner. **Action dispatch** sends a mediated action toward an external service. **Destination-mailbox acceptance** is what makes sending a message successful. **External output delivery** gets accepted output to someone outside the protocol. The bare phrase *Execution delivery* names none of them and should not be written. The cost of skipping the qualifier is not pedantry: "it was delivered" is true of a byte reaching a Driver, of a message accepted into a mailbox, and of an email landing in the editor's inbox — and those three facts support three entirely different conclusions.

## Revision

A **revision** identifies one version of one named value or contract. The discipline that makes revisions usable is a naming rule: always say which value's revision is meant, because there is no global "the revision" of an Execution, and nothing anywhere counts versions on its behalf.

Seven kinds appear across these pages, and they stay separate because their creators, their change points and the questions they settle are all different.

| Revision kind | Who moves it, and when | What comparing two values settles |
|---|---|---|
| Accepted progress revision | The Kernel, whenever it accepts replacement progress | Was this proposal built on the currently accepted continuation, or on a superseded one? |
| Base progress revision | The Activation, which copies the accepted version the exchange starts from | Which starting point was this answer computed against? |
| Definition and Runtime contract revision | The publisher of the code, or of the integration contract | Which program is this, and how is this exchange read? |
| Progress codec version | The Runtime or Driver publisher | Can this stored continuation still be decoded with compatible code? |
| Operation and schema revision | The operation's owner | Under which contract were these arguments validated, approved and settled? |
| Resource and state revision | The resource service, whenever its value changes | Is the value this decision assumed still the value that exists? |
| Action evidence revision | The trusted settlement or reconciliation path | What is known now — appended, without rewriting what was known before? |

Reading two kinds together shows why the discipline exists. "Progress revision 4, writer epoch 2" says that attempt 2 is working from accepted progress 4. It does not say that attempt 1 produced an accepted revision 5, or that four attempts preceded this one, or that anything else about the Execution is in its fourth version. The two labels live in different domains — one counts accepted continuations, the other ranks efforts at one exchange — and the only fact connecting them is that one dispatch pinned both.

Nor is any revision obliged to be an integer. Where no total order is required, a hash, an opaque token or a version string serves. What every kind owes its readers is the comparison its row of the table names, and nothing more.

## Acceptance, boundary and receipt

**Acceptance** is the Kernel's authoritative decision to record a request or a fact under the relevant contract — the moment a claim becomes part of what the Kernel will answer questions from. Several real events masquerade as acceptance, and each confusion has its own cost. Bytes arriving is transport. Passing validation is a property of content. [Admission](actions.md#admission-and-physical-action-attempt) authorizes an attempt at something in the world. None of the three, by itself, records anything as having happened, and a system that treats one of them as acceptance ends up reporting progress nobody ever decided on.

An **atomic acceptance boundary** names the facts that must commit together or not at all. *Boundary* here is a consistency requirement, not machinery: one process may contain several boundaries, one boundary may span components, and the term implies neither a machine nor a transport edge. Where these pages mean an API, an interface or an ownership line, they say so instead. [The atomic decisions table](../mechanisms/execution-cycle.md#atomic-decisions-across-the-system) lists which facts share each boundary.

A **receipt** is retained evidence that one specific request was accepted at one named boundary, at a stated revision or position. It may be handed back to a caller; it is not inherently a message from Kernel to Runtime, and it carries no permission of its own. What it proves is its named decision — and, by construction, nothing adjacent to that decision.

Six boundaries issue receipts, because the six decisions are made at different times by different authorities, and a caller needs to interrogate each one without borrowing evidence from another:

| Boundary | The one question its receipt answers |
|---|---|
| Creation or input ingress | Was this create or input request accepted? |
| Activation dispatch intent | Was this exact dispatch recorded before sending? |
| Outcome acceptance | Was this Runtime proposal accepted? |
| Effect admission | Was this physical attempt authorized and recorded? |
| Effect settlement | Was this evidence accepted? |
| Child or message operation | Was this child-creation or routing operation accepted? |

There is accordingly no single receipt per Execution, and inventing one is not a harmless abbreviation. The overreach the separation blocks is everyday: an Outcome-acceptance receipt proves that a proposal *containing* a publication request was accepted, and proves nothing whatever about whether anything was published; that question belongs to admission and settlement, which issue their own receipts for it. A Kernel-minted [timeout Event](core.md#timeout-event) is accepted too, but that acceptance is bookkeeping inside the Kernel's own machinery and introduces no seventh receipt for callers to ask about.

An **acceptance position** orders accepted facts within the record that owns them — enough to resume a read, or to say which of two decisions from the same authority came first. It is not a clock. No ordering across two accepting domains, or across two Executions, is promised, because none can be observed.

Retrieving evidence is itself a scoped operation. Lookup authenticates the caller and bounds what that caller may see *before* revealing anything — the content first of all, but the very existence of the record too. A refusal must not distinguish "no such record" from "a record exists and it is not yours": not by its message, not by its shape, not by how long it takes to come back. A lookup that betrays the difference is an enumeration oracle; anyone who can guess identifiers can map another principal's work without ever being granted sight of any of it.

A retained decision is retrievable only while its retention contract keeps it. Within retention, an exact duplicate of an earlier request is answered from the recorded decision; once retention lapses, the same request text is simply a new request. That change of meaning at expiry is consequential rather than cosmetic, which is why a deployment publishes what it retains and for how long, instead of letting spent keys quietly resurrect — [retention and deletion](../mechanisms/evidence.md#retention-and-deletion) owns the published contract.

What a receipt concretely is stays open. Whether it is an opaque token or a structured tuple, how it is serialized, and how a request key is hashed for lookup are implementation choices. What these pages fix is narrower and more durable: which decision a receipt names, and what it is and is not evidence of.
