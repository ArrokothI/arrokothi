# Runtime roles and context vocabulary

[Core coordination vocabulary](core.md) named the four parties the Kernel deals with, and the objects that pass between them. Almost everything on this page sits inside just one of those parties — the [Execution Runtime](core.md#execution-runtime) — and describes how its own code organizes itself, not anything the Kernel accepts, enforces, or even notices. A Workflow's branches, an Agent's planning loop, a Skill loaded into either one: none of it is a Kernel-visible type, and the Kernel's picture of an Execution does not grow a new case merely because the code advancing it happens to use one of these patterns.

That is the one rule every definition below assumes, so it earns a sentence of its own before any term needs it: **a Runtime-internal structure has no Kernel mailbox, no authority binding, and no lifecycle of its own.** It cannot receive an [Event](core.md#event) directly — only the [Execution](core.md#execution) has a [mailbox](core.md#mailbox). It cannot hold [authority](actions.md#principal-and-authority) — only the Execution has an authority binding, and a Runtime-internal name for a slice of work is not a second principal wearing the Execution's clothes. And it has no lifecycle of its own to watch — there are no states here beyond the Execution's own five. Wherever a term below starts to sound like it might have its own inbox, its own permissions, or its own way of ending, that reading is wrong; the definition will say what the term actually has instead.

None of that makes this vocabulary optional busywork. Choosing between a fifty-line function, an Agent, a Workflow, or an entire third-party framework kept whole is a real design decision, and so are the narrower ones nested inside it: how work is divided into pieces, what a model is shown and how its eventual choice is honored, and what a piece of borrowed code is allowed to see and to bring in from outside. The words below exist so those decisions can be discussed precisely, without smuggling any of them across the boundary the paragraph above just drew. [Composition](../mechanisms/composition.md), [context construction](../mechanisms/context.md) and [state and memory](../mechanisms/state.md) specify how these pieces actually behave together; this page only names them.

## A first example

Return to the report [Execution](core.md#execution) from [core coordination vocabulary](core.md#a-first-example). Its Runtime is built as a **Workflow**: a fixed pipeline of steps, one of which lets a model choose how to proceed.

```text
intake figures → outline (model picks: trend analysis, or comparison to last year)
    → the chosen analysis → join → editor review → publish
```

The branch choice is where an **Agent** pattern shows up inside this otherwise fixed Workflow: for that one step, a model reads the intake and decides which analysis fits, rather than the pipeline's author deciding in advance. Each arrow above is a **Stage**, and everything between "outline" and "join" runs inside a **local branch** that Stage owns — invisible to the Kernel as separate work, because none of it has asked to be seen. One of the intake figures arrives as a scanned exhibit that needs OCR before anything can read it, and the Runtime hands that off to a **local worker**: a pool of OCR processes the Runtime manages entirely on its own, with no child Execution and no [Kernel Worker](operations.md#kernel-worker) anywhere in the picture.

Before the model is asked to pick a branch, the Runtime has to decide what it will actually see. A **context compiler** assembles that **context**: this quarter's figures, last quarter's published report for tone, and the house style guide — not the full archive of every report ever filed, because more context is not automatically better context. Two of those three inputs arrived together, packaged: the Runtime loaded a **Skill** called `house-style`, whose **package manifest** named the style guide file it wanted read and the phrasing conventions it wanted followed. Loading it enriched this one Runtime's context; it granted the Skill nothing.

Once the model has a branch to justify and a draft to propose, it needs a name for "publish this." A **projection** renders the stable [operation](actions.md#operation) `publish_report` as the **callable alias** `send_report`, and an **invocation binding** fixes, for this one invocation, that `send_report` means `publish_report` at its current schema revision. Sitting right next to it, offered through the identical call syntax, is `jot_note` — a **local control** that only appends to the Runtime's own scratch pad and never crosses the Kernel boundary at all. The **invocation snapshot** of the `send_report` call — which alias, which revision, which arguments — has to survive until that call resolves; the wider catalog the model chose from is only a **context cache**, and recomputing it before the reply arrives changes nothing about what the reply meant.

What the model may read and write while doing any of this is bounded by a **view**: it can read the current draft and the figures behind it, but not last quarter's internal review notes, and it can propose a new value only for the fields the current principal is actually allowed to change. Handing any of that to the model — the figures, the style excerpt, the schema behind `send_report` — is **disclosure**, authorized at the moment it happens, never implied by whatever some earlier request was shown.

Behind `publish_report` sits a **service** — the publication system — whose own implementation the Runtime never sees. Getting the editor's sign-off uses an **interaction template**: a fixed question, "Approve, reject, or edit?", filled in with this draft's own summary. And the OCR job from two paragraphs back is tracked by an **async handle** — a correlator the local worker keeps so that whichever OCR process finishes first can be matched back to the intake step that asked for it.

None of the last five paragraphs created a second Execution, a second mailbox, or a second authority binding. That is the entire point of the vocabulary: it lets all of this be discussed exactly, while leaving the Kernel's picture of the Execution exactly as small as [core coordination vocabulary](core.md) described it.

## How a Runtime is shaped

The four terms below answer one question: who decided the next step — a graph fixed in advance, a model choosing freely, or work the Runtime keeps entirely to itself? The answer changes nothing the Kernel sees. It changes a great deal about how a later failure gets diagnosed, because a wrong step in a fixed graph and a wrong step a model chose freely are wrong for completely different reasons, and get fixed by completely different people.

### Agent

An **Agent** is a Runtime built so that a model directs its own control flow: at each step, the model decides what happens next, rather than code written in advance deciding for it.

Naming this pattern earns its keep the first time something goes wrong. A bad step inside a fixed graph points at a bug in the graph, and the fix is a code change. A bad step an Agent's model chose freely points at a bad decision under the information the model had, and the fix might be better context, a different model, or a narrower set of choices — none of which touches a single line of control-flow code, because there wasn't any to touch. Keeping "which kind of wrong was this" answerable is also why [attribution and gates](../mechanisms/evidence.md#attribution-and-gates) keeps Agent Runtime quality as its own failure domain, separate from Kernel correctness: a benchmark that conflates the two can make a perfectly correct Kernel look responsible for a model's bad judgment call.

The roles an application gives to pieces of an Agent's own reasoning — planner, evaluator, router, retriever — are that application's vocabulary, not additional Kernel kinds. Whatever names the application chooses for its internal division of labor, the Kernel still sees exactly one Execution and one Runtime performing all of it; none of those role names crosses into anything this page's opening rule forbids a Runtime-internal structure from having.

### Workflow

A **Workflow** is a Runtime that primarily follows a control flow fixed in advance — though that fixed flow can still include branches and loops whose direction a model selects.

"Primarily fixed" is the load-bearing phrase, because a Workflow that lets a model choose one branch has not thereby become an Agent. Agent and Workflow describe two ends of a spectrum — how much of the next-step decision is delegated to a model at any given point — rather than two mutually exclusive kinds a Runtime must pick one of, and nothing stops one Runtime from mixing both freely at different steps. The report's own pipeline is fixed everywhere except one step: intake, join, editor review and publish are all decided in advance, and only the middle branch choice is delegated to a model. That makes it a Workflow with one Agent-shaped decision inside it, not a contradiction needing a third category.

Agent and Workflow can also share implementation machinery and coexist inside one Runtime without conflict, because neither is a Kernel type the two patterns need to be kept apart from each other for. The Kernel has no way to tell which pattern built a given Execution, and no reason it would ever need one: [Execution Runtime](core.md#execution-runtime) already established that native algorithms stay opaque to the Kernel, and a Runtime's choice between these two shapes is exactly the kind of internal algorithm that opacity was built to cover.

### Stage and local branch

A **Stage** (or local node) is a defined unit of input, computation, output and transition inside a Workflow Runtime. A **local branch** owns its own intermediate control flow and result within the enclosing Runtime.

Giving a step this kind of boundary lets a Runtime reason about "did this piece finish, and what did it produce" entirely on its own terms, without asking the Kernel anything — but that reasoning stays entirely the Runtime's job, because a Stage has no independent Kernel mailbox, authority, or lifecycle of its own. It is this page's opening invariant, applied at the smallest scale this vocabulary names. In the pipeline sketched above, everything between the outline Stage and the join Stage runs inside a local branch: the chosen analysis, whatever it needed to compute, stays invisible to the Kernel for as long as the Workflow chooses not to surface it. [Composing work inside a Runtime](../mechanisms/composition.md) specifies how joins, barriers, and concurrent branches actually behave once more than one of them is running at a time; this page stops at naming the pieces that mechanism composes.

### Local worker

A **local/delegated worker** is internal work a Runtime or native framework manages on its own. It is not automatically a child Execution, and it is not automatically a [Kernel Worker](operations.md#kernel-worker).

"Local" describes who is accounting for the work, not where it physically executes, and that distinction is easy to lose because the two usually coincide. The OCR pool from the first example may in fact run in another process, or an entirely separate remote service, complete with its own native retries and its own job identifiers — none of which promotes it to Kernel-visible status. Work becomes Kernel-visible only the moment an application deliberately creates a [child Execution](operations.md#child-and-ownership) for it, a decision made because that work needs its own address, its own authority, and its own recovery — never merely because it happens to run somewhere else. A sentence using the bare word "worker" without saying which one is almost always underspecified, because it is ambiguous with a [Kernel Worker](operations.md#kernel-worker), a completely different role owned by a completely different page.

A **supervisor** that inspects a local worker's result and decides whether to retry it is, by the same logic, an application or Runtime role rather than a Kernel concept — it is simply code exercising judgment over work it already owns. Once that judgment concerns a real child Execution rather than a local worker, though, the ancestry and cancellation policy it can actually rely on is owned elsewhere: [finite expansion and supervision](../mechanisms/communication.md#finite-expansion-and-supervision) specifies the accounting and controls a declared supervision policy is built from, and this page's supervisor is only the role that chooses to use them.

## What a Runtime shows a model and how it reads the reply

A model only ever sees what a Runtime decides to put in front of it, and only ever acts through a name the Runtime chose to expose. The three terms below cover both halves of that exchange: building what goes in, and retaining enough of one invocation's own context to make sense of whatever eventually comes back.

### Context

**Context** is the information selected for one computation. It does not need to be retained once that computation ends.

Calling it "context" instead of "state" is a deliberate choice of word: state persists because something decided it should, while context is assembled — or reassembled — fresh for whichever request is being made right now, and a Runtime is free to discard it the instant that request returns. A **context compiler** performs that assembly: it selects, retrieves, redacts, or summarizes authorized information for one request.

A context compiler does not grant access to anything it selects, and it does not assert that an inferred claim it includes is true merely by choosing to include it — it is a rendering step, and rendering something more prominently is not the same act as vouching for it. [Building context](../mechanisms/context.md#select-information-without-changing-its-status) owns the actual selection rules, including the boundary this definition exists to protect: selection is allowed to shorten, reorder, or redact, but it must never change what something *is* — an inference arriving dressed as an assertion is exactly the failure a context compiler exists to prevent, never a shortcut it is permitted to take on a busy day. The report's own compiler pulled this quarter's figures, last quarter's published report, and the house style guide, and stopped there on purpose, rather than including every report the application has ever filed.

### Projection and invocation binding

An **operation projection** renders selected, stable [operations](actions.md#operation) as provider-facing names and schemas a model can read. A **callable alias** is the name the model actually sees — `send_report`, in the example above — and it is not the operation's own stable identity: the alias can be renamed, and the operation behind it can move to a new schema revision, independently of each other and at different times. An **invocation binding** is what ties the two together for exactly one invocation. It fixes which operation — and which revision of that operation's contract — a given alias meant, together with the input or state that mapping depended on, at the moment the model actually made its choice.

The reason this needs its own durable record, rather than a lookup performed again whenever a reply arrives, is that a model's reply can arrive long after the moment it was produced: after an ordinary retry, after an authorized takeover, after the very catalog the model was shown has since moved on. Resolving that reply against today's alias table, instead of the one the model actually saw, would let a renamed alias silently redirect an old answer toward an operation the model never chose. Concretely: if `send_report` was bound to `publish_report@2` at the moment the model replied, and the catalog has since repointed that alias at `publish_report@3` — a revision that added a required `distributionList` field the model was never shown — the reply still resolves against revision 2, because that is the revision the binding recorded, not whatever the alias happens to mean today. [Fixing bindings for each invocation](../mechanisms/context.md#fix-bindings-for-each-invocation) owns the exact retention and refusal rules that keep that promise; this page fixes only what the binding is for.

A **local control** changes Runtime-local planner or scratch state, and nothing else. It keeps that typed origin even when it is offered to the model through the identical call syntax as a mediated operation: `jot_note` and `send_report` can look, to the model choosing between them, like the same kind of thing. Only one of the two can ever become an [Effect](actions.md#effect), and which one is decided by what the Runtime actually built the control to do — never by how the call happens to be spelled on the wire.

None of operation projection, callable alias, or invocation binding is itself a Kernel object. The Kernel eventually sees the [Effect](actions.md#effect) that names `publish_report`; it never sees the alias the model used to ask for it, and it has no need to.

### Invocation snapshot and cache

An **invocation snapshot** preserves enough of a native request and its bindings to interpret its response, or to continue it, later. A **context cache** is an optional, recomputable optimization, and nothing more than that.

The two are easy to conflate because both look, from the outside, like "something the Runtime kept around from before" — but confusing them costs a real guarantee. Work still in flight depends on its invocation snapshot, so that snapshot cannot be discarded on the theory that it is just a cache entry waiting to be rebuilt; rebuilding it might quietly produce a binding for a newer catalog, which is precisely the failure the previous section's invocation binding exists to rule out. A context cache exists purely to avoid recomputation, and losing it costs latency, never correctness — recomputing the catalog a model was shown changes nothing about a binding already fixed for an invocation already in flight. A **provider prompt cache** is a third, unrelated thing: an optimization the model provider itself controls, never this Runtime, and it stays exactly that — a caching detail that can speed up a request, never a source of authority or disclosure the Runtime did not already grant on its own.

The invocation snapshot of the report's `send_report` call — its alias, its bound revision, its arguments — has to survive until that call resolves. The wider catalog it was chosen from is only a context cache, and recomputing that catalog before the reply arrives changes nothing about what the reply meant when it was made.

## What a Runtime is allowed to see and to package

The last three terms bound what crosses into a Runtime from outside it: what a principal has actually authorized it to see, and what an external package is allowed to bring along with it. Each is worth stating plainly, because every one of them is easy to mistake for a grant of authority when it plainly is not one.

### View and disclosure

A **view** is a selection of readable fields or objects, and writable targets, authorized for the current principal. **Disclosure** is content, descriptors, or metadata actually sent to a Runtime, a model, or a remote retrieval service.

The two terms stay apart because "authorized to be seen" and "actually shown" are different moments, and collapsing them hides a real failure: a view can be entirely correct while one particular disclosure still exceeds it, if whatever renders the request includes something the view never cleared. That gap is exactly why [before sending](../mechanisms/execution-cycle.md#before-sending) pins an authorized [execution view](#view-and-disclosure) as part of what it records before an Activation ever goes out, rather than trusting a Runtime to have applied the view correctly on its own good faith.

A scope label attached to a piece of information locates it; it does not grant a view over it, and holding a view describes what is authorized to be shown, not the fact that any particular disclosure has already happened. Metadata is where this boundary is most often crossed by accident: an internal precondition token, a global revision counter, a cache-hit signal — none of these look like content, and every one of them can leak a hidden change to a reader who was never shown the change itself. Exposing any of them is its own disclosure decision, not a free side effect of exposing something else that seemed harmless. In the report, the view let the model read the current draft and its figures while withholding last quarter's internal review notes, and it authorized a proposed value only for the fields this particular principal was actually allowed to change.

### Skill and package

A runtime **Skill** packages instructions, references, assets or scripts, and optionally a root composition, so that a Runtime can be enriched — or made to invoke work — without the package itself being an Execution or an authority grant. A **package manifest** describes a Skill's source and version, its entry points, its bindings, and the requirements it requests.

The rule this definition exists to protect is concrete: a manifest that requests `publish_report` is a request the deployment answers, exactly like any other request for authority, and it is never a self-service grant — loading a Skill can never widen what its enclosing Execution is permitted to do, however confidently the manifest asks. [Content is not authority](../mechanisms/authority.md#content-is-not-authority) states the general form of this rule; a Skill is its single most concrete instance, precisely because a Skill is packaged to look like it has already earned trust before anyone has actually decided to extend it any.

One naming collision is worth heading off directly, because it sits inside this very repository: a runtime Skill is not the same thing as this repository's own `.agents/skills/` — the coding-agent workflow skills that help maintain ArrokothI's own code. The two share a word and nothing else; one is a Runtime-facing packaging concept this page defines, the other is tooling for the people and agents writing ArrokothI itself, and reading a reference to one as a reference to the other is a pure accident of vocabulary. Loading `house-style` in the first example enriched the report Runtime's context with phrasing guidance; it granted the Skill nothing, and it could not have widened the report Execution's authority even if its manifest had asked.

### Service and interaction template

A **service** exposes selected input, result, and interaction contracts while keeping its own implementation private. An **interaction template** supplies parameterized, predefined or context-driven input for one of those interactions. An **async handle** correlates a piece of native external work with whatever eventually answers it.

None of the three implies a new mandatory Kernel entity, and none is a portable descriptor hierarchy the Kernel has to understand. They are ordinary application-level shapes for structuring how a Runtime talks to something outside itself, and each is worth distinguishing from an [operation](actions.md#operation) for the same reason: an operation is what the Kernel actually admits and settles, while a service is what sits behind one, opaque to everything on the Kernel's side of that boundary. The publication system behind `publish_report` is a service in exactly this sense. The fixed "approve, reject, or edit?" question put to the editor, filled in with this draft's own summary, is an interaction template. And the correlator tracking which OCR process eventually answers which intake step is an async handle — three ordinary shapes for talking to the outside world, none of them a second Kernel type in disguise.

---

Every term on this page describes something inside, or immediately around, one Runtime — never a second lifetime, a second authority holder, or a second thing the Kernel has to open the box to understand. That is not a ceiling on how expressive Runtime code is allowed to be: a Workflow instructed by a Skill, delegating pieces of its work to local workers, projecting operations under aliases a model resolves through bindings fixed at the moment it chose them — all of that can be as rich as an application needs it to be. It is a ceiling on where any of that richness is allowed to end up. Nowhere on this page does it reach the Kernel's mailbox, the Kernel's authority ledger, or the Kernel's account of what state an Execution is in — and that is exactly what makes the vocabulary safe to keep growing.
