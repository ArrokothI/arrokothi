# Systems, ownership, and competition

[Study home](README.md). All repository observations refer to the [pinned local revisions](evidence/source-manifest.json), not generic reputations. “Owns” below describes where design decisions and authoritative state concentrate; it is an architectural inference from the cited implementation.

## The important comparison

These systems overlap because they organize work around different persistent objects and adoption paths. They are not cleanly separated layers that inevitably need ArrokothI underneath them.

| System | Center of gravity | Architectural consequence | Natural reason to adopt |
|---|---|---|---|
| OpenClaw | Persistent assistant sessions, gateway, channels, and native execution environments | Routing, identity, policy, runtime ownership, and reliable delivery are tightly coordinated. | An assistant already connected to the user's communications and work environment. |
| Hermes Agent | An ongoing Agent in a working environment, with context, skills, tools, and continuity | Native session/context/tool lifecycle is part of the Agent's behavior, not incidental glue. | A capable extensible assistant that accumulates useful working practices. |
| Dify | Authored applications, their publication and operation, tenant-scoped resources | Workflow state, human forms, model/plugin strategies, app events, and product data meet in a platform control plane. | Build and operate an Agent/knowledge application with an existing product surface. |
| CrewAI | Developer-authored roles, tasks, crews, and event-driven Flows | Python composition, execution strategies, tools, feedback, and checkpointing optimize a developer workflow. | Express and ship collaborative automation in its native programming model. |
| ArrokothI today | Explicit logical Executions advanced through one Harness contract | Authority, Effects, Events, progress, waiting, and composition are modeled before a mature application surface. | Currently a semantic toolkit and research implementation; a production adoption reason remains unproven. |

Feature overlap is expected. Distribution, language, installed integrations, operating model, and the user's existing data often determine adoption more than the Agent loop. Coexistence is evidence that multiple products can be useful; it is not evidence of an unoccupied “kernel layer.” Mature projects can internalize a useful kernel mechanism without adopting a new kernel product.

## OpenClaw: the gateway has become an execution environment

The inspected OpenClaw is not adequately described as a messaging wrapper around a single embedded Agent. Its [harness types](../../../openclaw/src/agents/harness/types.ts) distinguish native versus host ownership of model and authentication, compatibility requirements, runtime artifacts, and supported host capabilities. Its [plugin SDK entry point](../../../openclaw/src/plugin-sdk/agent-harness.ts) exposes runtime integration. [Runtime selection](../../../openclaw/src/agents/harness-runtimes.ts) routes configured harnesses and caches selection information. These are direct architectural analogues to part of ArrokothI's heterogeneous-runtime proposal.

The strongest analogue is the [host capability contract](../../../openclaw/src/agents/harness/host-capability-types.ts): scoped tool surfaces, activity assertions, approval handling, prepared environments, and usage reporting are supplied around a native runtime. ArrokothI should study this as an existence proof that a host can govern selected facilities while preserving native cognition. It is not proof of a universal portable ABI: these are in-process TypeScript interfaces within OpenClaw's own session, configuration, plugin, and policy environment.

Authority depends on provenance and ownership, not just an exposed tool list. The [tool policy pipeline](../../../openclaw/src/agents/tool-policy-pipeline.ts) composes named narrowing layers. Codex adapter [authority tests](../../../openclaw/extensions/codex/src/app-server/run-attempt-runtime.authority.test.ts) distinguish scheduled authority, principal/profile restoration, configured endpoint identity, and disallowed invocation origins. The [dynamic-tool contract tests](../../../openclaw/extensions/codex/src/app-server/openclaw-owned-tool-runtime-contract.test.ts) cover hook ordering, argument transformations, and tool result mediation. These tests were inspected, not executed in this study. They refute a comparison in which OpenClaw is assigned only ambient, unstructured permissions and ArrokothI all explicit governance.

Its [task registry](../../../openclaw/src/tasks/task-registry.types.ts) separates runtime categories, execution status, delivery status, notification policy, and owner identity. [Task access checks](../../../openclaw/src/tasks/task-owner-access.ts) require trusted ownership context rather than accepting a correlation key as authority. The distinction between a task succeeding and its result reaching a user has accumulated real implementation weight.

That weight appears in [delivery recovery](../../../openclaw/src/infra/outbound/delivery-queue-recovery.ts), [unknown-send reconciliation](../../../openclaw/src/infra/outbound/delivery-queue-reconciliation.ts), and [lease tests](../../../openclaw/src/infra/outbound/delivery-queue-lease.test.ts). Delivery needs exact prepared payloads, ownership leases, expiry, retries, and transport-specific evidence when a send's outcome is uncertain. A generic “retry failed operation” primitive cannot resolve this. ArrokothI already distinguishes uncertainty conceptually; OpenClaw supplies a concrete reminder that each external system must provide the evidence required to reconcile it.

**Strategic implication:** OpenClaw can be a user-facing ingress and native execution service, and it is also a competitor for the logical environment around Agents. Embedding its gateway/session machinery inside ArrokothI would usually duplicate control planes. Integrate a scoped task/service endpoint, preserving OpenClaw's session and channel ownership. Attempt a deeper host-tool bridge only for actions whose ownership can be made exclusive. Treat its current adapter tests as stronger evidence than a clean but untested ArrokothI interface.

## Hermes: useful cognition includes the environment lifecycle

Hermes' [Agent implementation](../../../hermes-agent/run_agent.py), [context engine interface](../../../hermes-agent/agent/context_engine.py), and [context compressor](../../../hermes-agent/agent/context_compressor.py) show an Agent whose request construction, session history, compaction, tool observations, cleanup, and provider routing are interdependent. The context interface explicitly separates request-only selection from permanent transcript mutation. Compaction protects selected history, prunes tool output, uses bounded auxiliary work and fallback behavior, and handles runtime context propagation. These are operationally significant parts of native Agent quality.

Its [progressive tool bridge](../../../hermes-agent/tools/tool_search.py) already offers search, description, and invocation over deferred tools. Catalog exposure has size-aware representations and essential tools can remain direct. The code's own historical note about reduced use of a deferred clarification tool is a useful caution, not a reproduced empirical result: discoverability can save tokens while hiding the action a model most needs. Do not assume a hierarchy or a small scout automatically improves on this mechanism.

[Tool dispatch](../../../hermes-agent/model_tools.py), particularly `handle_function_call`, resolves bridge calls to underlying tools before middleware and approval-related processing. Optional enabled/disabled tool scopes and native hooks exist; it would be false to describe all Hermes dispatch as unguarded. However, native defaults and globals—such as resolved tool sets and environment/session facilities—are not an ArrokothI tenant or authority boundary. Adapting them requires tracing the actual dispatch path, including fallback and indirect calls.

[Environment backends](../../../hermes-agent/tools/environments/base.py) preserve shell state across command invocations and connect to multiple physical execution environments. [Filesystem checkpoints](../../../hermes-agent/tools/checkpoint_manager.py) provide shadow-repository recovery for working files. This is valuable workspace undo, which differs from durable execution progress and external-action reconciliation. The similarly named [checkpoint resumption test](../../../hermes-agent/tests/integration/test_checkpoint_resumption.py) concerns batch progress, so it must not be cited as arbitrary Agent crash recovery.

[Async delegation](../../../hermes-agent/tools/async_delegation.py) combines live workers with a persistent task/delivery ledger and routes completion into a new parent turn. Owner process identity, stale work, delivery claims, retention, and restored completion are separate concerns. [Restored ownership tests](../../../hermes-agent/tests/tools/test_restored_delegation_ownership.py) specifically defend recovered outputs from delivery under the wrong owner scope. [Child execution cleanup](../../../hermes-agent/tools/delegate_tool_child_run.py) handles cancellation ancestry and resources that an abstract spawn/return diagram misses.

Hermes is oriented toward personal/workspace continuity, but “single-user only” would overstate the evidence: the checkout also contains [hosted-room policy checkpoints](../../../hermes-agent/gateway/hosted_room_policy_checkpoint.py). The correct question is which concrete identity, storage, and tool paths a deployment exercises, not whether the project's original audience permits a blanket security label.

**Strategic implication:** the first useful reuse is a native Hermes job with explicit input, result, environment scope, and cancellation. Forcing its entire session into ArrokothI's current `AgentExecutorRequest.information` would discard or duplicate context ownership. Small algorithms or a physical environment backend may be reusable, but the engineering cost lies in removing implicit home directories, globals, registries, and cleanup assumptions—not just importing a class.

## Dify: application control plane, with substantial runtime reuse already

Dify owns the relationship among authored applications, tenants, published configuration, tools/knowledge, runs, human forms, and observable output. That is a product and operations boundary larger than an execution kernel.

A crucial source-reading correction: the current API imports **`graphon==0.7.0`**, declared in [API dependencies](../../../dify/api/pyproject.toml). The graph engine is not all implemented under the local API tree. This study inspected Dify's use of it, not absent `graphon` internals. The [Agent node](../../../dify/api/core/workflow/nodes/agent/agent_node.py) and [plugin Agent strategy](../../../dify/api/core/agent/strategy/plugin.py) show dependency injection and platform context around strategy execution. Native node output and log events are not ArrokothI Execution identities merely because both represent work.

The [pause persistence layer](../../../dify/api/core/app/layers/pause_state_persist_layer.py) persists graph state together with the response-stream filter and translates engine pause identifiers into application-owned human-form identities. [Human input service](../../../dify/api/services/human_input_service.py) handles expiry, forms, identity, and resumption routing. A [container integration test](../../../dify/api/tests/test_containers_integration_tests/core/workflow/test_human_input_resume_node_execution.py) exercises human-input graph resumption with database fixtures. This is real machinery beyond a visual DAG; it does not prove atomic recovery of every arbitrary node side effect.

The checkout also contains a newer **`dify-agent`** runtime. Its [dependencies](../../../dify/dify-agent/pyproject.toml) use Pydantic AI and related harness libraries. Its [runner](../../../dify/dify-agent/src/dify_agent/runtime/runner.py) coordinates streamed execution, output validation, deferred human tool calls, snapshots, and budgets. The [layer compositor](../../../dify/dify-agent/src/agenton/compositor/core.py) orders dependency layers and validates snapshot hydration. Dify already demonstrates selective reuse of cognition and runtime implementation while retaining its application semantics.

The most relevant Machine analogue is its [runtime backend contract](../../../dify/dify-agent/src/dify_agent/runtime_backend/protocols.py). Immutable home snapshots, workspaces, persistent bindings, and operation-local leases have distinct lifetimes. Acquisition must report a lost binding rather than silently replace it. Destruction must honor workspace preservation. The [server facade](../../../dify/dify-agent/src/dify_agent/server/execution_bindings.py) exposes those lifecycle operations. The [physical runtime's Go types](../../../dify/dify-agent-runtime/internal/server/types.go) concern shell jobs, output offsets, waiting, and termination. This is an environment abstraction with concrete recovery semantics; it is not the same proposal as ArrokothI's bounded logical Program IR.

**Strategic implication:** use a published Dify application as an external service and keep Dify responsible for its graph, forms, app state, and tenant lifecycle. Do not adopt the graph persistence layer and then independently reconstruct the same run in ArrokothI. Source extraction is also not presumptively permissive: the [root license](../../../dify/LICENSE) adds multi-tenant service and frontend conditions to Apache terms. A reuse decision must examine the exact component and intended deployment; a dependency used by Dify has its own license and is a separate candidate.

## CrewAI: native programming and orchestration, not just role prompts

[Crew](../../../crewAI/lib/crewai/src/crewai/crew.py) defines tasks, roles, execution processes, validation, state restoration, and checkpoint/fork entry points. The framework's value includes its Python authoring model, native execution conventions, and ecosystem. Many users need that coherent development experience more than a framework-neutral vocabulary.

The current execution path matters: [the old executor](../../../crewAI/lib/crewai/src/crewai/agents/crew_agent_executor.py) is deprecated; the current [Agent executor](../../../crewAI/lib/crewai/src/crewai/experimental/agent_executor.py), despite its directory name, is implemented as a **Flow** and includes ReAct and plan/execute machinery. The [Flow runtime](../../../crewAI/lib/crewai/src/crewai/flow/runtime/__init__.py) gives these strategies a shared execution substrate. This is a direct counterexample to assuming that Agent and Workflow must be fundamentally different runtime machines. Their control policies can differ while computation machinery is shared.

[SQLite Flow persistence](../../../crewAI/lib/crewai/src/crewai/flow/persistence/sqlite.py) includes saved state and pending feedback. [Human feedback](../../../crewAI/lib/crewai/src/crewai/flow/human_feedback.py) supports synchronous or asynchronous feedback and routing. [Checkpoint runtime](../../../crewAI/lib/crewai/src/crewai/state/runtime.py) and the [checkpoint listener](../../../crewAI/lib/crewai/src/crewai/state/checkpoint_listener.py) reconstruct state and runtime associations. It would be incorrect to compare ArrokothI's waiting model with a CrewAI caricature that cannot persist or resume anything.

The guarantee boundaries still differ. Event-driven snapshots are not proof that a remote side effect and its checkpoint commit atomically. Human feedback directing a Flow is not automatically approval bound to the exact payload later dispatched. [Tool hooks](../../../crewAI/lib/crewai/src/crewai/hooks/tool_hooks.py) can modify or block calls, but an adapter must verify every path, hook ordering, credentials, and restart behavior before promising complete mediation.

**Strategic implication:** a Crew can participate as a native task with bounded external services and an opaque native checkpoint. Reusing its entire Flow as a second authoritative lifecycle inside each ArrokothI Stage is unlikely to simplify anything. A deeper tool bridge might be valuable for a specific crew, but generic Crew import/translation is a large compatibility project with little initial evidence of payoff.

## Mature durable runtimes are essential baselines

The four requested systems do not exhaust ArrokothI's competition. If the product claim concerns recovery, compare with a plain service plus a database and with an established durable runtime.

Temporal explicitly recommends idempotent Activities and explains the crash window between an external action and reporting its result. Completed results can be replayed while uncertain attempts may execute again. ArrokothI's explicit unknown outcome is useful only if its surrounding recovery workflow reduces real harm or integration effort beyond a properly written application on that substrate. [Temporal Activity definition](https://docs.temporal.io/activity-definition).

Restate's durable steps journal nondeterministic operation results and define replay restrictions. Its architecture uses durable logs, partition ownership, and fencing. This suggests reusing reliable execution mechanisms while retaining ArrokothI's action/authority semantics. It also raises the burden of proof for building another scheduler/journal stack. No claim of universal exactly-once external action follows. [Durable steps](https://docs.restate.dev/develop/ts/durable-steps), [architecture](https://docs.restate.dev/references/architecture).

LangGraph's interrupts use checkpointed state and explicit resumption, with constraints on node re-execution and side effects around interruptions. It belongs in the native Agent/workflow baseline set. ArrokothI should compare the work required to implement exact consent, action recovery, and heterogeneous ownership—not count the existence of a wait primitive as its advantage. [LangGraph interrupts](https://docs.langchain.com/oss/python/langgraph/interrupts).

These are documentation-level supplementary comparisons, not repository audits or performance results. A small team should implement one durable baseline deeply enough to make a decision, not build production adapters for all three.

## Where differentiation could survive

The plausible opening is an application spanning independently valuable engines, business operations, and humans, where developers repeatedly have to reconstruct authority, uncertain action recovery, and causal ownership. ArrokothI could offer a smaller, testable common contract and diagnostic surface.

The opening disappears if all engines can simply run as opaque jobs behind an existing workflow service with ordinary application policy. It also disappears if obtaining ArrokothI's claimed guarantees requires replacing each engine's cognition, storage, and tool system. A clean ontology without lower integration cost, stronger observable correctness, or better useful work per budget is not a strategic moat.

The initial buyer hypothesis should therefore be one small team with an already heterogeneous, consequential application—not “all AI developers” or a framework author seeking another abstraction. Find a repeated coordination failure and prove that this boundary removes it. Ecosystem breadth, marketplace size, and polished Studio are later distribution choices, not substitutes for that proof.
