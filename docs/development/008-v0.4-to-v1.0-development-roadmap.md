## 1. Release strategy

The development goal is no longer:

```text
put every architectural idea into v0.4
```

The goal is:

```text
v0.4
  establish a coherent reference Agent kernel on top of Slices A-C
        ↓

v0.5-v0.7
  progressively implement the canonical composition, authority,
  memory, interoperability, concurrency, security, and durability seams
        ↓

v0.8
  architecture-complete experimental release
  all major canonical concepts exercised together in real programs
  APIs may still change based on evidence
        ↓

v0.9
  stabilization / compatibility / hardening / bake period
  avoid major new semantic surface
        ↓

v1.0
  publish the mature subset proven by v0.8-v0.9
  stable public contracts and conformance expectations
```

The important distinction is:

> **v0.8 is the integration-and-validation target. v1.0 is the maturity/stability target.**

A concept being canonical does not imply that every optimized backend, protocol binding, hosted feature, or advanced policy mechanism must ship immediately.

Development documents may propose APIs and migrations, but they do not redefine these meanings.

Prefer a testable end-to-end semantic path over broad type-system completion.

is more valuable than adding every possible descriptor field before one complete Agent path works.

### 2.5 Canonical rewrite creates a conformance retrofit gate

Slices A-C are a valuable green implementation baseline, but they were implemented before the latest canonical split clarified controller-local asynchronous resumption, interleaving, recursive composition, structured parallelism, principal-aware authority inputs, and the revised memory model.

Therefore:

> **“Implemented and green under the previous docs” is not the same as “conformant to the rewritten canonical docs.”**

Before adding the reference Agent, perform a focused current-code audit against the new canonical owners. Do not reopen correct A-C semantics wholesale; identify only concrete mismatches.

One mismatch is already known:

```text
current Workflow model access
  await provider.generate(...) inside controller Activation

canonical runtime
  slow controller-local model work may yield
  → ControllerResumption
  → no semantic Event
  → WAITING when nothing else is runnable
  → READY when resumption settles
```

The pre-D retrofit must therefore establish the minimum generic `ControllerResumption`/controller-local suspension seam and migrate Workflow LLM Stage / LLM Adapter model invocation onto it, with fast/slow semantic equivalence.

This does **not** mean turning model calls into Effects, PendingOperations, or Events. It means bringing the already-implemented Workflow path into conformance with the canonical distinction:

```text
PendingOperation
  runtime-mediated semantic work
  → Event on settlement

ControllerResumption
  controller-local async work
  → controller continuation runnable on settlement
```

If the focused audit finds other concrete A-C divergences caused by the canonical rewrite, fix only those required to make the v0.4 substrate honest before building Agent semantics.

### 2.5.1 Audit result (2026-08-31)

The audit ran against the implemented A-C path at 441 passing tests, 8 passing benchmark-subject tests, and a clean typecheck. It found **one** blocking defect, presenting on three code surfaces, and no others.

```text
ports/controller.ts
  ControllerNext = continue | await_event | complete | fail
  no status expresses controller-local suspension

execution/context.ts, interaction/event-envelope.ts, runtime/event-router.ts
  waitingFor is an Event condition and nothing else
  the only WAITING -> READY path requires a mailbox append
  so yielding would have required inventing an Event

controllers/workflow/model-access.ts -> llm-stage.ts, adapters.ts
  await provider.generate(...) inside the Activation
  the scheduler claim is held for the whole provider latency
  runLLMStage runs up to maxModelPhases provider round trips in one Activation
```

These are one blocker, not three: fixing any one alone changes nothing.

Everything else audited as conformant or as a later-slice gap with an adequate seam. In particular the following were checked and need **no** pre-D change: the closed Event vocabulary (no local-result kind, no protocol kind); audit/journal/trace records kept out of mailboxes; the generic `PendingOperation` record; Effect fast/slow equivalence and the inline-budget/deadline separation; single-writer Activations via scheduler exclusion plus revision CAS; Harness-derived `WAITING` and `READY`-before-`RUNNING`; `WAITING` not closing the mailbox; the absence of any Definition-cycle rejection anywhere in validation; `rootExecutionId`/`ownerExecutionId` lineage already propagated and already visible to authorization; `Stage != Execution`; `ModelCallableDeclaration` as Stage-local binding; `ModelCapabilitySpec` as provider projection; `LocalResource` as materialized-local-only; the Catalog/Authorizer/Executor split with final authorization on the concrete payload; zero external dependencies in core; and settlement authority kept separate from Effect authority.

Two seams were confirmed adequate rather than fixed. `DeferredSlots` holds authority/active-view as opaque refs, so Slice D can type them without an A-C retrofit. `EffectAuthorizationRequest` carries no application principal facts, which the v0.4 authority requirement below explicitly defers; the field is additive when v0.5+ needs it.

One boundary is correct but fragile and should be watched in Slice D rather than patched now: `runLLMStage` computes the information context and the operation projection in the same function. They are separate computations over separate inputs today, so Slice C is conformant, but the Agent path must introduce them as distinct components rather than reproducing one function.

# Part I — v0.4: Reference Agent Kernel

## 3. v0.4 objective

v0.4 should make Arrokoth a coherent **Agent + Workflow execution kernel**, not a complete platform.

Slices A-C establish the Execution substrate, Event/Effect gateway, provider foundation, and Workflow Stage model. They remain the implementation baseline, but the canonical rewrite requires the focused conformance retrofit described in §2.5 before they are treated as the current semantic baseline.

After that gate, the main v0.4 goal is the first reference Agent implementation and the minimum authority/exposure machinery required for it to be semantically correct.

### Required v0.4 capabilities

```text
AgentDefinition / AgentSpec
AgentControlState
AgentController
reference AgentExecutor
provider-neutral model resolution
information-only context compilation
Harness-owned effective operation authority
ActiveOperationViewResolver
immutable per-invocation ModelOperationProjection
exact projection binding resolution
model-directed continue / respond / operation-call / stop
operation call → typed Effect proposal
Harness remains final authorizer
ControllerResumption for slow controller-local model calls
Workflow LLM Stage / LLM Adapter use the same controller-local resumption semantics
bounded Agent progression
```

The important v0.4 proof is:

> **A model-directed Agent can safely perform repeated operations and continue across slow model/tool results without any provider/framework/tool registry bypassing the Harness.**

### v0.4 concurrency requirement

Implement the minimum runtime behavior already required by the canonical runtime model:

```text
one controller-state writer per Execution
multiple independent Executions may run in parallel
slow model provider call may yield an Activation
ControllerResumption makes work READY when model result arrives
PendingOperation remains distinct from ControllerResumption
fast vs slow controller-local model completion is semantically equivalent
for both Workflow and Agent reference paths
```

v0.4 does **not** need the final parallel Workflow branch API, general transactions, or distributed leases.

#### v0.4 suspends exclusively, and that is deliberate

An Execution suspended on a `ControllerResumption` must wait on that resumption **and nothing else**. No arriving Event may produce a second Activation while the continuation is outstanding; the Event is queued and observed after the resumption settles.

```text
v0.4   yield one model call, and forbid other semantic progress while it is suspended
v0.5   allow another Activation to mutate controller state before the result returns
```

This is what makes v0.4 free of stale-continuation risk without any stale-continuation machinery: the race the canonical runtime warns about needs an intervening Activation, and v0.4 has none. It must be an **asserted, tested property**, not an accident of what the current Workflow controller happens to do — because the moment v0.5 lets a mailbox Event wake a resumption-suspended Execution, the risk becomes real, and a v0.4 that had quietly allowed it would have shipped the v0.5 problem a release early.

Record the suspending Activation's controller revision on the resumption record from v0.4. It is one field with no policy attached, and it is what v0.5's rule below checks. Adding it later means migrating persisted records.

Relaxing this restriction is v0.5 work and is gated on the minimal stale-continuation rule in §4 shipping with it.

### v0.4 authority requirement

Implement only the authority/exposure subset needed to prove Agent operation selection:

```text
Catalog operation descriptor
        ↓
Harness-owned effective operation authority
        ↓
deterministic Active Operation View
        ↓
immutable model projection
        ↓
concrete Effect re-authorization
```

Do not implement the complete future principal/delegation/policy ecosystem yet.

### v0.4 interoperability proof

Keep the narrow proof from `007`:

```text
one native portable operation
  ↔ one synchronous MCP Tool import/export path
```

if it can be added without delaying the Agent kernel. It is an architecture proof, not a requirement to implement MCP Tasks, Resources, Prompts, subscriptions, A2A, or general service export in v0.4.

> **Landed 2026-09-01**, after Slice D acceptance and the behavioural baseline. Both directions are
> implemented in `packages/interoperability/mcp` against official MCP TypeScript SDK v2 (the
> 2026-07-28 spec line), with `packages/core` unchanged apart from one corrected comment. Details,
> the supported/refused schema subset, the result/error/unknown mapping, and the deferred list are
> in [`011-mcp-synchronous-operation-proof.md`](011-mcp-synchronous-operation-proof.md).

### Explicitly not required for v0.4

```text
full recursive Agent/Workflow composition
complete child authority delegation model
Derived Semantic Memory provider
parallel Workflow branch API
heterogeneous progressive discovery engine
A2A service adapter
Agent Skills loader/registry
hostile-code isolation backend
fully durable restart recovery
public Skill/package signing
federated workload identity
Cedar/OpenFGA integration
Mem0/Graphiti integration
advanced shared-resource transactions/leases
```

# Part II — v0.5: Recursive Composition and Interaction

## 4. v0.5 objective

Make Agent and Workflow composition work recursively under explicit runtime identity and delegation boundaries.

Primary capabilities:

```text
spawn Agent / Workflow
call Agent / Workflow
Agent Stage
Workflow Stage
child terminal result correlation
owner/root relationships
structural spawn budget
basic child cancellation/supervision hooks
send / ask
peer message routing
RequestUserInput
mechanical confirmation baseline
```

### Authority expansion

Introduce the first real child-delegation path:

```text
requested child authority
  ∩ creator delegable authority
  ∩ application/runtime policy
  ↓
effective child authority
```

The concrete grant representation may remain small, but child authority must not be inferred from the Definition or model request.

### Runtime/liveness proof

Exercise:

```text
recursive Definition composition is legal
lineage structural budget prevents unbounded spawn
wait-for dependencies are observable
one blocked continuation does not automatically close mailbox
A↔B request/reply cycles can progress when semantics permit
```

The last two capabilities introduce controlled interleaving between Activations. A minimal stale-continuation rule must therefore ship with the first such interleaving; it cannot wait until v0.8.

v0.5 is also where the v0.4 exclusive-suspension restriction is lifted. Those are one change, not two: the moment a mailbox Event may wake a resumption-suspended Execution, a continuation computed at revision N can resume after an Activation committed N+1. Do not relax the restriction in one release and add the rule in the next. The revision recorded on every resumption record since v0.4 is the input the rule checks.

The first implementation may deliberately choose a simple policy such as:

```text
suspended continuation records controller revision N
intervening semantic commit advances revision
old continuation settles
  → reject/invalidate/re-evaluate unless controller proves it is merge-safe
```

The exact long-term API remains open, but v0.5 must not allow a continuation computed from stale controller assumptions to commit silently.

### v0.5 conformance examples

```text
Workflow → Agent → Workflow
Agent → two child Agents in parallel
Agent A asks Agent B while another dependency is pending
child with narrowed operation authority
child cancellation and terminal-result delivery
long-lived Agent requests user input and resumes
exact-payload confirmation invalidates after payload change
intervening Activation invalidates or safely re-evaluates a stale suspended continuation
```

# Part III — v0.6: Memory and Structured Concurrency

## 5. v0.6 objective

Implement the canonical memory distinctions and begin exercising deterministic parallel composition/shared-state semantics.

### Memory capabilities

```text
Structured Memory
  schema-bound explicit state
  explicit WriteMemory path
  provenance refs
  memory views

Working Notes
  Execution/branch-local scratch
  explicit child visibility/handoff

Artifacts / Files
  durable large work products
  resource/context references

Context compiler
  information selection only
  independent from operation projection
```

Introduce a provider seam for **Derived Semantic Memory** and a simple reference implementation sufficient to prove:

```text
source observation ≠ derived claim ≠ Structured Memory
provenance is retained
derived claim does not automatically grant authority
explicit promotion into Structured Memory is possible
```

A production-grade graph/vector memory backend is not required yet.

### Memory scope/view

Prove that memory form and scope are orthogonal:

```text
Execution/task/user/application/shared scope
  ×
Structured / Derived / Notes / Artifact
```

A scope identifier must not act as permission by itself.

### Structured parallelism

Begin implementing system-defined parallel Workflow branches without concurrent free mutation of controller state.

Target shape:

```text
fork
  ├── branch B local progress / Effects / child calls
  └── branch C local progress / Effects / child calls
        ↓
explicit join
        ↓
defined merge/reducer/conflict behavior
```

The first version can support branch-local results plus deterministic join before general shared-state reducers.

### Shared-memory/resource conflicts

Add the first optimistic concurrency primitive where needed, preferably version/precondition semantics for Structured Memory rather than a universal mutex.

Prove a lost-update conflict is detected instead of silently becoming timing-dependent last-write-wins.

Slice G.0 (doc [`024`](024-slice-g0-structured-memory-optimistic-conflict.md)) implements exactly this
first primitive: an optional `WriteMemoryProposal.expectedRevision` whole-view compare-and-set and a
distinct `memory.write_conflict` observation, with a tested lost-update proof. Field-level / merge
semantics remain later work.

Slice G.1 (doc [`025`](025-slice-g1-minimal-workflow-fork-join.md)) implements the first slice of the
parallel-branch target above: authored `{ to: "fork" }` / `{ to: "join" }` Workflow topology,
branch-local `WorkflowParallelState` (own visit / input snapshot / progress / result per branch), an
explicit join as a distinct controller step exposing an immutable authored-order `WorkflowJoinContext`
to one downstream Function Stage, deterministic result/failure ordering, and a fail-closed refusal of
branch Effects — for a branch body that is exactly one Function Stage. No child Executions, no new
Stage/Effect/Event kind, control-state version 2 → 3.

Slice G.2 (doc [`026`](026-slice-g2-parallel-branch-dependencies.md)) extends that: a branch may be
any adapter-free Stage kind (`function` / `llm` / `agent` / `workflow`) and may hold a real
asynchronous dependency — a `UseCapability` Effect, a child `call`, or a slow model call — while
staying a branch of one Workflow Execution. It adds a runtime dependency-set (union) wait
(`ControllerNext` `await_dependencies`, `ExecutionWait` `dependencies`, fail-closed
preflight before Effects, atomic multi-registration commit, and a final transactional re-read that
selects READY when an Event or recovered resumption is already satisfied) that is deliberately *not*
`interleave`; branch-qualified Effect correlation and
ControllerResumption keys; and a `parallel_branch_memory_write_deferred` fail-closed. No new
Stage/Effect/Event kind (`dependencies` is a wait kind only), no branch Execution, control-state
version 3 → 4. Multi-Stage branches, nested forks, branch Adapters, branch emissions, reducers,
merge, cancellation propagation, concurrent Structured Memory branch writes, and branch Working
Notes remain G.3+.

# Part V — v0.8: Architecture-Complete Experimental Release

## 7. v0.8 objective

v0.8 is where the major canonical concepts must work **together**, not merely exist as separate prototypes.

The target is not API stability yet. The target is architectural completeness plus evidence.

### Runtime integration

By v0.8, exercise:

```text
many Executions running concurrently
controller-local asynchronous resumption
PendingOperation/Event settlement
recursive composition
structural budgets
wait-for diagnostics
cancellation/supervision
parallel Workflow branches
shared-resource conflict semantics
restart durability
```

Resolve, through implementation evidence, whether `PendingOperation` and `ControllerResumption` remain separate semantic/runtime records or share a broader internal suspension substrate while preserving their semantic distinction.

### Stale continuation safety

By v0.8, **generalize and harden** the minimal stale-continuation safety introduced with the first interleaving semantics in v0.5.

Prove a concrete policy across all relevant controller-local and runtime-mediated suspension cases:

```text
model/continuation computed from controller revision N
intervening Activation commits N+1
old result returns
```

Possible mechanisms include revision binding, invalidation/re-evaluation, restricted interleaving, or controller-specific merge semantics. The important requirement is that stale assumptions do not silently commit.

### Authority integration

By v0.8, prove the full canonical chain across child composition and large catalogs:

```text
application principal/policy context
        ↓
root/effective authority
        ↓
attenuated child delegation
        ↓
Active View / progressive discovery
        ↓
immutable model projection
        ↓
concrete Effect re-authorization
```

A simple built-in policy implementation is mandatory. Cedar/OpenFGA adapters are optional experiments, not prerequisites for semantic correctness.

### Memory integration

By v0.8, prove:

```text
Structured Memory explicit assertion
Derived Semantic Memory extraction/retrieval with provenance
Working Notes visibility/handoff
Artifacts as durable work products
memory form × scope
explicit derived→structured promotion
context compilation independent of operation projection
concurrent Structured Memory conflict behavior
```

At least one nontrivial Derived Semantic Memory provider/backend should be exercised. It may be the reference implementation or an adapter to an existing project.

### Interoperability integration

By v0.8, maintain real conformance examples for:

```text
native operation ↔ MCP
exported Agent/Workflow service ↔ A2A or ordinary API
instruction Skill ↔ Agent Skills profile
long-running external handle ↔ Arrokoth runtime correlation
external auth/input requirement without changing Execution authority
```

Not every protocol feature must ship. The goal is to prove the portable layer is real and not only documentation.

### Durability

v0.8 should support a durable reference path sufficient to recover:

```text
Execution/lifecycle
controller state
mailboxes/Event cursors
PendingOperations
ControllerResumptions/equivalent
Effect journal/settlement state
child/owner relationships
structural/runtime budgets
projection snapshots needed by suspended calls
memory/resource refs
```

A simple durable implementation is preferable to prematurely adopting a heavyweight external runtime. External durability backends can be evaluated after the Arrokoth conformance suite exists.

### Security integration

The isolated profile should have an executable conformance suite and one credible implementation path. It is acceptable for the trusted-local profile to remain the default developer path.

Security claims must be profile-specific; v0.8 should not imply that every embedded SDK use is sandboxed.

# Part VI — v0.9: Stabilization and Bake

## 8. v0.9 objective

v0.9 should avoid adding broad new semantic surface.

Use it to learn which v0.8 concepts are actually mature enough for v1.0.

Focus on:

```text
API naming and simplification
compatibility/migration rules
failure semantics
restart/recovery testing
load/concurrency testing
security testing
protocol conformance
provider compatibility
benchmarking Active View/discovery/context compilation
memory quality/provenance evaluation
observability and diagnostics
documentation/examples
public SDK ergonomics
```

### Required stress programs

Maintain a small set of “architecture breaker” programs, for example:

```text
1. long-lived Agent with slow model calls + incoming peer messages
2. recursive divide-and-conquer Agent tree under structural budget
3. A↔B cyclic request pattern that is not a deadlock
4. genuine deadlock candidate with diagnostics/timeout policy
5. parallel Workflow branches with conflicting Structured Memory writes
6. stale model result after controller interleaving
7. Agent using thousands-entry operation catalog with progressive discovery
8. derived-memory contradiction/supersession with provenance
9. Agent/Workflow exported through MCP/A2A/API without leaking kernel identities
10. crash/restart while capability, child call, model call, and confirmation are pending
11. hostile Stage/plugin attempting direct secret/network/filesystem bypass
12. child with narrower authority/memory visibility than parent
```

v0.9 is successful when these programs behave predictably and changes are increasingly implementation/ergonomic rather than semantic redesigns.

# Part VII — v1.0: Mature Contract

## 9. v1.0 objective

v1.0 should publish **the mature subset proven by v0.8-v0.9**, not every experiment ever attempted.

A feature should be part of the v1.0 stable contract when it has:

```text
clear canonical semantic owner
reference implementation
conformance tests
failure/recovery semantics
security implications documented
usable developer API
at least one realistic application/example
no known ambiguity that requires redefining neighboring concepts
```

### Expected stable core

The intended v1.0 center is:

```text
Execution / Harness / Activation
Agent + Workflow
Event / Effect
PendingOperation + controller-local resumption semantics
spawn / call / send / ask
structured parallel Workflow composition
authority / delegation / Active View / exact projection binding
Structured / Derived / Notes / Artifacts memory model
portable Operation / Resource / service / Skill layer
MCP + A2A + Agent Skills compatibility where proven
trusted-local and explicitly advertised hosted security profiles
durable wait/resume/recovery semantics
```

### What v1.0 does not require

v1.0 does not need every optional backend or ecosystem integration.

The following can remain optional/post-v1.0 if the core is mature without them:

```text
all policy engines
all memory providers
all sandbox providers
all durability engines
AG-UI/A2UI/MCP Apps/ACP integrations
federated public Agent network
UCAN-like distributed delegation proof format
public Skill marketplace/registry
full information-flow/taint system
learned operation selector
multiple distributed scheduler implementations
```

Stable ports plus one well-tested implementation are better than many shallow integrations.

# Part VIII — Feature maturity levels

## 10. Use maturity labels instead of pretending every implemented feature is stable

From v0.5 onward, development/release notes should classify large capabilities as:

```text
Reference
  minimum implementation proving semantics

Experimental
  usable for integration/evaluation; APIs may change

Candidate
  intended for v1.0 unless evidence reveals a problem

Stable
```

# Part IX — What not to pull forward prematurely

## 11. Important future work that should remain evidence-driven

The canonical [`../future-plan.md`](../future-plan.md) intentionally contains open questions. `008` does not turn all of them into mandatory v0.4 work.

In particular, do not prematurely require:

```text
one universal Suspension type
one universal transaction/lock API
one specific Derived Semantic Memory graph schema
one specific policy engine
one specific durability engine
one universal Skill manifest
one global heterogeneous registry implementation
one learned discovery selector
one distributed/federated identity standard
one frontend Agent protocol
one sandbox technology
```

The architectural requirement is to preserve the semantic boundary and prove replaceability with real adapters/tests.
