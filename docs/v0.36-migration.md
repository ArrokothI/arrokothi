# Migrating to Agent SDK v0.36

v0.36 repairs authoritative observations, structured-record semantics, external-effect outcomes,
and Gemini workflow planning without changing the primary `AgentRuntime -> AgentHarness ->
CapabilityGateway` architecture.

## Knowledge observations

Agentic native Knowledge capabilities now return the complete provider-neutral `KnowledgeResult`
to the same inner loop. Document observations include the executed query and ranked chunk text;
record observations include the normalized query, matches, `totalMatched`, and `totalRecords`; web
observations include the executed query and result titles, URLs, snippets, and publication metadata.
`KnowledgeRetrieved.result` durably records the same provider-neutral evidence; compact delegation
summaries avoid storing a second full copy in the delegation audit event.

Native Knowledge capabilities are canonical. `recordQueryTools(...)` remains supported for older
response-tool integrations, but new agentic definitions do not need that wrapper.

An invocation-local cache replays an identical normalized native Knowledge read in the same phase
and mutation epoch. A successful or outcome-unknown mutation, a phase change, a different source,
kind, filter, sort, limit, or query prevents equivalence. Cache replay returns the evidence and an
`observationProvenance.kind = "cache_replay"` marker; it does not add model strategy advice.

## Record field semantics

The existing shorthand remains valid:

```ts
fields: { active: { kind: "boolean" } }
```

Source authors may now add provider-neutral semantics:

```ts
fields: {
  supplier_region: {
    schema: { kind: "string" },
    description: "Contractual service region assigned by the supplier registry.",
    examples: ["north-sector"],
  },
}
```

Descriptions and optional primitive examples are JSON serializable. Field descriptions reach the
Knowledge catalog, workflow planner context, native record capability description/input metadata,
and compatibility record query tool description. Field examples reach the Knowledge catalog,
workflow planner context, and compatibility record query tool description; native agentic
capabilities intentionally expose descriptions without examples. Core transports this metadata and
never invents field meaning. Malformed metadata, blank descriptions, and examples that do not match
the declared field schema are definition validation errors.

## External side effects

`ToolResult` now distinguishes:

- success (`ok: true`);
- definite failure (`ok: false`, with omitted or `"definite_failure"` outcome);
- ambiguous remote outcome (`ok: false, outcome: "outcome_unknown"`).

Legacy failure results without `outcome` remain definite failures. An exception thrown by an
external-side-effect executor is conservatively recorded as outcome unknown; exceptions from reads
and ordinary writes remain definite failures.

`ToolExecutionContext.idempotencyKey` is newly required. It is runtime owned, stable for the
session-scoped logical authorized action/replay, and recorded on execution events. Executors should
pass it to remote APIs that support idempotency.
Successful entries written with the pre-v0.36 unscoped ledger key are still recognized during
replay, so upgrading an existing durable session does not re-dispatch those completed effects.

The same material external action is dispatched at most once in an external user turn. A definite
failure may be retried later only through a fresh payload-specific confirmation when the tool uses
required confirmation. No-confirmation external tools have no implicit retry policy. Outcome-unknown
actions are never automatically retried. A changed payload always requires fresh confirmation.

Durable events use `ToolExecutionFailed` for definite failure and
`ToolExecutionOutcomeUnknown` for ambiguity.

## Gemini workflow wire format

Core's provider-neutral record filter value remains polymorphic. Gemini workflow structured output
no longer receives the nested `anyOf` representation for that value. The Gemini adapter projects it
to a JSON-text string on the provider wire and deterministically restores strings, numbers,
booleans, or primitive arrays before `parseTurnPlan` and record-field validation. Core remains
provider neutral and its validation remains authoritative.

The wire-format tradeoff is that a string which itself looks like JSON (for example `"true"`) must
be emitted as a JSON string literal on the wire (for example `"\"true\""`) to remain a string.
Malformed JSON text remains plain text and is still checked against the selected record field.

## Compatibility

- Existing bare record field schemas continue to work.
- Existing executor failures without `outcome` continue to mean definite failure.
- Executor implementations must accept the new required `ToolExecutionContext.idempotencyKey`.
- Native record Knowledge and `recordQueryTools(...)` both remain available; native Knowledge is
  canonical for agentic execution.
