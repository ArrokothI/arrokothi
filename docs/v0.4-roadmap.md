# Agent SDK v0.4-v0.5 Roadmap

This document records the current direction after reviewing Agent_SDK against the distinction between
LLM workflows and agents: workflows follow application-defined paths, while an agent dynamically
chooses its next action from observations and available capabilities.

Agent_SDK should remain a **stateful agent control plane**, not become an unbounded self-modifying
prompt runner. The central rule remains:

> Models choose and propose. Runtime validates and authorizes. Executors/environment establish truth.

The roadmap is intentionally staged so benchmark evidence can decide whether architectural
simplifications are worth their latency, token, and reliability cost.

---

## Current architecture assessment (v0.37)

`AgentHarness(strategy: "agentic")` plus `StrandsLoopEngine` is an agentic loop: the model may choose
Knowledge or Tool capabilities in an unknown order and number of iterations, observe results, and
choose the next step or final response.

`AgentHarness(strategy: "workflow")` / `TwoPassHarness` remains a bounded workflow compatibility path.

Agentic mode still has one workflow-shaped stage before the loop: semantic Preflight. In agentic
mode Preflight currently owns only user-established structured Memory proposals, Working Notes, and
coarse Flow signals. Retrieval, task decomposition, and Tool choice belong to the loop.

The long-term question is therefore not "is Agent_SDK an agent?" but whether Preflight remains useful
as a separate state-reconciliation call once the loop can safely propose the same state changes.

---

## Immediate correctness work before/alongside v0.4

### Refresh authoritative context after an in-loop Phase transition

This is the highest-priority correctness issue identified in the current design.

Today the agent-loop `CompiledContext` / system prompt is created once before `engine.run()`, while the
capability catalog is dynamic. An `action_result` may transition Flow during the loop. On the next
model call the tool set can therefore reflect the new Phase while the system prompt still describes
the previous Phase objective/instructions.

Required invariant:

```text
phase/state mutation
→ authoritative context refresh
→ capability refresh
→ next model decision
```

The implementation may recompile/rebind the current context or restart a bounded inner-loop segment,
but the model must never receive a new Phase capability envelope paired with a stale Phase prompt.

Add regression tests covering:

- `action_result` Phase transition followed by another model iteration;
- new Phase objective/instructions visible on that iteration;
- new Phase Knowledge/Tool scope visible on the same iteration;
- old Phase-only capabilities unavailable;
- trace records showing the context/Phase boundary clearly.

Do not change broader agent semantics until the current benchmark run is preserved as a baseline.

# v0.4 — single-agent state and authority

The goal of v0.4 is to make the existing agent loop a better owner of **working state**, while keeping
runtime authority and retaining Preflight as a safe/default compatibility mechanism.

## 1. Loop-writable Working Notes

Allow the agent loop to create, revise, and remove Working Notes.

Working Notes remain:

- non-authoritative;
- unavailable as the sole source for side-effecting Tool arguments;
- bounded by count/size and optional TTL;
- attributable to source events/observations;
- excluded from permanent AgentDefinition changes.

Prefer workspace semantics over unbounded append-only notes. Explore keyed operations such as:

```text
note_upsert(key, text, ttl?)
note_delete(key)
```

Anonymous append notes may remain available, but the agent should be able to replace stale
interpretations rather than accumulate contradictory notes indefinitely.

## 2. Loop-native structured Memory proposals

Allow the agent loop to **propose** writes to declared structured Memory fields.

Do not expose a primitive that means "the model writes authoritative memory". The model proposes a
key/value plus evidence/basis; the runtime validates schema, field policy, provenance, and authority.

Keep the existing provenance distinction:

```text
user_claimed
model_inferred
tool_verified
host_provided
```

Default authority policy:

- `user_claimed`, `tool_verified`, and `host_provided` may become authoritative when the field permits;
- `model_inferred` is advisory unless the field explicitly opts into inferred authority;
- the model can never grant itself authority.

Structured fields remain optional builder hints, not required form slots. An agent with an empty
`memorySchema` should remain fully valid and may rely on Working Notes instead.

### Evidence for user-established values

A loop proposal that claims a value came from the user should identify the source event and, where
practical, a supporting verbatim span. Runtime can mechanically verify source existence/span
membership and schema compatibility. This does not make semantic entailment perfectly mechanical,
but it is stronger and more inspectable than silently converting every model proposal to
`user_claimed`.

## 3. No default second-LLM judge

Do **not** add a general judge-model call for every Memory proposal, Phase suggestion, Tool request, or
terminal answer.

A second model does not create ground truth; it adds another probabilistic decision, latency, cost,
and failure mode. Prefer, in order:

1. schema/type validation;
2. provenance and source-evidence checks;
3. deterministic Flow conditions;
4. CapabilityGateway policy;
5. explicit user confirmation for consequential ambiguity;
6. an optional semantic judge only when the application cannot express the requirement
   deterministically and the value justifies another model call.

If semantic validation is later added, it must be opt-in and measured separately in call/token
metrics.

## 4. Keep Flow runtime-owned in v0.4

Flow remains a coarse, inspectable state machine. The model may emit semantic signals; the runtime
evaluates the application-defined transition conditions and declaration priority deterministically.

For v0.4, this is sufficient:

```text
model/planner observes semantics
→ emits allowed signal or commits allowed Memory proposal
→ runtime evaluates predefined transition conditions
→ runtime changes Phase (or not)
```

No judge model is needed merely to "approve" a transition whose condition is already defined by the
application.

## 5. Measure the cost of loop-native state operations

Before collapsing Preflight, add/retain metrics for:

- model calls per external turn;
- prompt/input tokens per model call;
- tool/capability schema token cost;
- state-write capability requests;
- note writes/replacements/deletions;
- Memory proposals/commits/rejections by provenance;
- Phase transitions and context refreshes;
- latency to first final user-facing response.

An important experiment is whether exposing Note/Memory operations as ordinary tools causes simple
turns to require an additional model call. If so, v0.45 should test a first-call state-update envelope
instead of forcing every state mutation through a tool-use round trip.

# v0.45 — preflight collapse, Focus, Flow agency, and MCP

v0.45 is the experimental release for reducing duplicate semantic interpretation and increasing
agent autonomy without allowing the model to rewrite application authority.

## 1. Preflight collapse experiment

Compare:

```text
A. current
Preflight state reconciliation
→ agent loop

B. unified
first agent iteration
→ state proposals + next action/direct answer
→ runtime commits/rejects
→ continue only if necessary
```

The target is a common direct-response path with one model call, while preserving provenance,
replayability, confirmation, and inspectable accounting.

Questions to answer with benchmark evidence:

- Does unified mode reduce total latency/tokens?
- Does Memory recall degrade?
- Do false or missed Memory writes increase?
- Does exposing state operations make prompts materially longer?
- Does a weaker model fail because one call now has too many responsibilities?
- Can providers/Strands express state proposals and a useful next action without forcing an extra
  round trip?

Do not remove Preflight until unified mode demonstrates a clear reliability/cost advantage or the
runtime can choose between the two strategies safely.

## 2. Separate Agent Focus from Runtime Phase

Phase currently mixes two ideas:

- cognitive focus (`objective`, `instructions`);
- authority/capability scope (`toolNames`, `knowledgeSourceIds`, transitions).

Introduce or experiment with an agent-writable **Focus/Subgoal** working-state field:

```text
focus_set("Compare the final two options on commute time")
```

Focus is advisory and mutable by the agent. It must not replace the immutable Agent goal or invariant
rules.

Recommended authority hierarchy:

```text
Application-owned, immutable/versioned
  global goal
  invariant rules
  schemas / authority policies
  allowed Flow graph

Runtime-owned authoritative state
  current Phase
  authoritative structured Memory
  current capability envelope

Agent-owned working state
  Focus/Subgoal
  Working Notes
  hypotheses / temporary plan
```

## 3. Agent-requested Phase transitions

For semantic transitions that are awkward to express as Memory/tool conditions, allow the agent to
request a transition only among application-declared candidates.

Conceptually:

```text
phase_request(to, reason)
→ runtime checks that the edge is declared and its policy allows an agent request
→ proceed / deny / guide
```

Keep hard transitions deterministic. Example: a successful irreversible handoff may automatically
enter `completed`; the agent should not choose whether that fact happened.

The model must never create arbitrary new Phases or rewrite the Flow graph at runtime.

## 4. Optional semantic validation policy

If benchmark/use cases show a real need, add an opt-in per-field/per-transition semantic-validation
policy, for example:

```text
none | judge | user_confirm
```

This is for genuinely semantic high-value ambiguity, not as a blanket validation layer.

## 5. MCP interoperability

Add MCP as a Tool/Knowledge provider adapter beneath Agent_SDK authority.

MCP discovery/calls must still pass through Agent_SDK concepts:

```text
MCP server
→ MCP adapter/provider
→ ToolDefinition / Knowledge capability
→ CapabilityCatalog
→ CapabilityGateway
→ executor/call
→ authoritative ToolResult/KnowledgeResult
```

MCP descriptions/annotations are untrusted hints, never authorization. Preserve confirmation,
idempotency, phase scope, argument policy, audit, and ToolResult truth.

Also evaluate capability discovery/lazy exposure so a large MCP server does not inflate every model
prompt with an unnecessary tool catalog.

# v0.5 — broader agent platform

v0.5 should take the larger features that are useful but should not block proving the single-agent
state model.

## Skills

Define a provider-neutral, versioned `SkillDefinition` beginning with static/manual Skills:

- metadata plus instructions and referenced resources;
- explicit Phase/agent scoping;
- serialization and provenance rules;
- adapters for provider-specific Skill systems where semantics remain compatible;
- investigation of Strands-compatible Skill patterns and `SKILL.md` interoperability.

Automatic permanent Skill learning must not be the default. A later governed path may be:

```text
sessions / corrections / Working Notes
→ SkillProposal
→ offline evaluation
→ human approval
→ versioned Skill
```

The agent must never silently rewrite its permanent capabilities or invariant instructions.

## Subagents

Study isolated-context workers with:

- least-privilege capability scope;
- explicit input/evidence/result contracts;
- bounded budgets and cancellation propagation;
- parent-owned acceptance of results;
- durable trace semantics without exposing hidden reasoning;
- evaluation of whether Strands subagent facilities fit under Agent_SDK abstractions.

Teams and general multi-agent orchestration remain later questions unless benchmark tasks establish a
clear need.

## Long-term execution context

Investigate resumable execution/session mechanisms. Define when an agent should start with fresh
temporary context, when it may resume, what is persisted, how model history is invalidated after
authoritative state changes, and how migrations work across definition/model versions.

Agent_SDK Durable Session remains the truth source; framework conversation history remains an
execution optimization.

## Host integration

Design, but do not assume for v0.5 completion:

- browser/client SDK;
- production Host Context endpoint;
- authenticated-backend trust and identity rules;
- proactive external-event triggers with explicit consent and rate limits.

Host observations remain distinct from automatic agent invocation.

# Benchmark gates

The current benchmark run should be preserved as the **v0.37 baseline**. New designs should be
compared against it rather than assumed better because they appear more agentic.

At minimum compare:

| Metric | v0.37 baseline | v0.4 | unified v0.45 |
| --- | --- | --- | --- |
| task success / rubric score | measure | measure | measure |
| model calls per turn | measure | measure | measure |
| input/output tokens | measure | measure | measure |
| end-to-end latency | measure | measure | measure |
| Memory false writes | measure | measure | measure |
| Memory missed writes | measure | measure | measure |
| Flow/Phase correctness | measure | measure | measure |
| unsafe/incorrect Tool attempts | measure | measure | measure |
| direct-answer one-call rate | measure | measure | measure |

A more "agentic" implementation is not automatically better. Prefer the simplest architecture that
achieves equal or better correctness with acceptable cost and latency.

# v1.0 readiness

**v1.0 is the first formal/stable release.** Before v1.0, require:

- public API cleanup;
- removal/deprecation completion for duplicate Harness/loop concepts;
- documented SemVer policy;
- stable `AgentDefinition` serialization and versioning;
- documented package boundaries;
- complete migration guidance;
- end-to-end commercial examples;
- session concurrency and transaction review;
- crash/retry/idempotency tests;
- security review;
- provider/integration failure semantics;
- observability contract;
- formal benchmark evidence across representative subjects;
- production deployment guidance;
- generated API reference;
- compatibility matrix;
- proof that no framework-specific type leaks through core.
