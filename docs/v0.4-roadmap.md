# Agent SDK research roadmap: v0.4 and beyond

This document is the active evidence-gated roadmap after freezing the P01/P02 v0.37 benchmark baseline.
It intentionally does **not** assign detailed release numbers beyond v0.4 before the next prospective
benchmarks. Later version boundaries should follow evidence rather than architecture aesthetics.

The core design rule remains:

> Models choose and propose. Runtime validates and authorizes. Executors/environment establish truth.

Agent_SDK should remain a stateful agent control plane. More model calls, more autonomy, more tools, and
more framework machinery are not improvements by themselves. Prefer the simplest architecture that
preserves the required correctness, authority, truthfulness, and auditability.

---

## Current baseline: v0.37 is frozen

The frozen P01/P02 benchmark and its full audit live under:

```text
benchmarks/results/v2-six-subject-run-1/
```

Start with:

```text
benchmarks/results/v2-six-subject-run-1/final-analysis/RESULTS.md
```

P01/P02 are calibrated development/regression benchmarks, not held-out generalization tests.
The current baseline therefore answers "what does v0.37 do on the tasks we have studied?", not
"is this architecture universally better?"

### What the baseline actually showed

The important comparison is not a single leaderboard score.

**P01**

- Agenerateor and Arrokothai were both effectively perfect on conclusive deterministic assertions.
- Agenerateor had stronger semantic requirement scores.
- Blinded pairwise comparison preferred Arrokothai overall, driven especially by usefulness and
  conversational coherence rather than a clear correctness advantage.

**P02**

- Arrokothai was much stronger than Agenerateor on deterministic, state/action-grounded correctness.
- Arrokothai was also substantially stronger on semantic requirement satisfaction and truthfulness.
- Yet blinded user-facing pairwise comparison preferred Agenerateor over Arrokothai.

**Efficiency**

Arrokothai used materially more model calls:

- P01: about 2.96 calls/user-turn vs Agenerateor 2.00.
- P02: about 3.20 calls/user-turn vs Agenerateor 2.00.

Agenerateor subject-token accounting was unavailable in this run, so do not claim a controlled token
ratio between the two implementations.

### Current interpretation

The evidence supports a narrower claim than "Arrokothai is better":

> Explicit runtime/state/authority abstractions can improve execution-grounded correctness on tasks
> with consequential structured state and actions, but those guarantees currently have meaningful
> inference-call overhead and do not automatically improve user-facing conversational quality.

This is the design problem for the next stages: preserve the control-plane benefit where it matters,
while avoiding architecture tax where it does not.

# Immediate v0.4 goal: correctness before new features

v0.4 should be deliberately narrow.

Do **not** use the frozen P01/P02 results as a reason to immediately add more agent machinery. The next
release should first make the existing runtime match its own intended semantics.

## 1. Fix authoritative context refresh after in-loop Phase/state mutation

This is the highest-priority known correctness defect.

Today the agent-loop `CompiledContext` / system prompt can be constructed before `engine.run()`, while
the capability catalog may change after an in-loop state/Phase transition. That can produce a next
model call with the new capability envelope but stale Phase objective/instructions.

Required invariant:

```text
phase/state mutation
→ authoritative context refresh
→ capability refresh
→ next model decision
```

The implementation may recompile/rebind context or restart a bounded inner-loop segment. The model
must never receive a new Phase capability envelope paired with stale Phase context.

Required regressions include:

- `action_result` Phase transition followed by another model iteration;
- new Phase objective/instructions visible on that iteration;
- new Phase Knowledge/Tool scope visible on the same iteration;
- old Phase-only capabilities unavailable;
- trace records clearly identifying the Phase/context boundary;
- no duplicate executor dispatch introduced by the refresh mechanism.

## 2. Re-run provider conformance after the correctness fix

Keep provider-neutral schemas faithful and fail fast when an adapter cannot represent them.

The conformance gate should continue covering at least:

- structured output;
- nested object/map fields;
- arrays and optional fields;
- union/polymorphic schema handling;
- function/tool calls;
- tool-result continuation;
- workflow/structured-output paths that remain supported.

Run against the exact benchmark model before the next prospective experiment.

## 3. P01/P02 regression only — no retuning to win the old benchmark

After the Phase/context fix:

- re-run the relevant P01/P02 regression suite;
- verify no state/action/truthfulness regression;
- verify model-call changes separately;
- use unrelated synthetic tests for the changed invariant;
- do not alter old scenarios/evaluator rules because of the new result.

The frozen v0.37 result remains the baseline and must not be rewritten.

## Explicitly out of scope for this v0.4 correctness checkpoint

Do not add these before the P03 evidence gate merely because they are attractive abstractions:

- a workflow runtime;
- Preflight collapse/removal;
- blanket second-model semantic validation;
- unrestricted agent-written authoritative Memory;
- arbitrary runtime-created Phases;
- Skills/subagents/multi-agent orchestration;
- broad MCP integration work.

# Next evidence gate: P03 prospective comparison

After the v0.4 correctness fix and regression freeze, run the next prospective benchmark **before**
designing the next major architecture layer.

Compare frozen Agenerateor and frozen Arrokothai under the same model/settings/evaluator protocol.
Preserve the first valid prospective run before inspecting failures.

The purpose is diagnostic, not leaderboard optimization.

For sequential/process failures, classify them in this order:

1. **Observation defect** — the model did not receive an authoritative result it needed.
2. **Authority/policy defect** — the runtime could not mechanically prohibit an illegal next action.
3. **Model/ACI/prompt failure** — observations and legal-action boundaries were correct, but the model
   chose poorly.
4. **Fixed-process evidence** — observations and authority are correct, yet a required sequence remains
   repeatedly mishandled across reasonable prompts/models.

Only category 4 is evidence for adding a minimal Workflow runtime.

If P03 exposes generic runtime defects, fix those generically, then regress P01/P02 plus unrelated
synthetic cases before the next prospective benchmark.

# Workflow decision gate — only if P03 earns it

Agent and Workflow should share the same control plane:

```text
Agent:
  model selects next transition
  runtime bounds legality

Workflow:
  process definition selects next transition
  model handles bounded semantic work

Hybrid:
  workflow controls macro sequence
  model chooses locally within allowed nodes
```

If evidence requires a Workflow runtime, start with the smallest useful node set, such as:

- Agent/LLM;
- Tool;
- Condition;
- Set/Transform;
- Human approval;
- End.

Do not build a Dify-style visual workflow platform merely because workflows exist.

---

# P04 prospective generalization gate

After P03-derived changes are complete and P01/P02 + synthetic regressions are green:

1. freeze code, prompts, evaluator, model/settings, and comparison subjects;
2. run P04 prospectively;
3. preserve the first valid run before inspection;
4. compare Agenerateor vs Arrokothai without additional tuning.

P04 is the stronger check that P03-driven changes generalized instead of merely fitting P03.

After P04, a further unseen subject will still be needed for stronger generalization claims.

# Efficiency research after the prospective gates

The frozen P01/P02 result makes efficiency a first-class research question, but it should be studied
as an ablation rather than optimized ad hoc before P03/P04.

The key question is:

> Which Arrokothai model calls purchase correctness, and which are architecture tax?

A useful controlled experiment after the prospective gates is:

```text
A. Full Preflight
   semantic Preflight + current loop

B. No semantic Preflight
   deterministic/runtime validation + direct model loop

C. Selective Preflight
   invoke semantic reconciliation only for configured high-value/ambiguous cases
```

Keep ACI, prompt content, model, scenarios, and runtime authority as controlled as possible.
Measure separately:

- task correctness;
- state/action correctness;
- truthfulness;
- correction handling;
- model calls/user-turn;
- input/output tokens where all implementations expose them;
- latency;
- false/missed Memory writes;
- unsafe/incorrect Tool attempts;
- direct-answer one-call rate.

Do not combine quality and efficiency into one weighted score.

# Future directions — retain, but do not schedule prematurely

These remain plausible directions. Their release numbers should be assigned only after the evidence
gates above.

## Loop-writable Working Notes

Allow bounded agent-owned temporary workspace operations such as:

```text
note_upsert(key, text, ttl?)
note_delete(key)
```

Working Notes remain non-authoritative and cannot be the sole source for consequential side-effect
arguments.

## Loop-native structured Memory proposals

The model may propose writes to declared fields with evidence/provenance; runtime validates schema,
field policy, source evidence, and authority.

Preserve provenance distinctions such as:

```text
user_claimed
model_inferred
tool_verified
host_provided
```

The model must never grant itself authority.

## Focus/Subgoal separate from Runtime Phase

Keep runtime-owned Phase/authority separate from agent-owned temporary focus:

```text
Application-owned
  goal, invariant rules, schemas, allowed Flow graph

Runtime-owned authoritative state
  Phase, authoritative Memory, capability envelope

Agent-owned working state
  Focus/Subgoal, Working Notes, hypotheses/temporary plan
```

## Agent-requested Phase transitions

For genuinely semantic transitions, consider requests only among application-declared edges:

```text
phase_request(to, reason)
→ runtime validates declared edge/policy
→ proceed or deny
```

Hard transitions established by external results remain deterministic.

## Optional semantic validation

A second model does not create truth. Prefer deterministic validation, evidence checks, authority
policy, and explicit user confirmation first.

If needed, semantic validation should be opt-in for high-value ambiguity and measured as a separate
cost/failure source.

## MCP interoperability

MCP should sit beneath Agent_SDK authority:

```text
MCP server
→ adapter/provider
→ ToolDefinition / Knowledge
→ CapabilityCatalog
→ CapabilityGateway
→ execution
→ authoritative ToolResult/KnowledgeResult
```

MCP descriptions/annotations are hints, not authorization.

## Skills

Start with provider-neutral, versioned, static/manual Skills. Permanent learning should require an
explicit governed proposal/evaluation/approval path rather than silent self-modification.

## Subagents

If tasks justify them, study isolated-context workers with least privilege, explicit input/result
contracts, bounded budgets, cancellation propagation, and parent-owned result acceptance.

## Long-running execution and host integration

Durable Session remains the truth source. Framework conversation history is an execution optimization.
Future work may cover resumable execution, version migration, authenticated Host Context, and
consented external-event triggers.

# Release planning rule

Do not pre-commit to a sequence such as `v0.4 → v0.43 → v0.45 → v0.5` merely to organize ideas.

Use this sequence instead:

```text
frozen v0.37 P01/P02 baseline
→ v0.4 Phase/context correctness fix
→ P01/P02 + synthetic regression
→ freeze
→ P03 prospective diagnostic
→ evidence-driven generic changes
→ regression + freeze
→ P04 prospective generalization
→ efficiency / Preflight ablations
→ assign later release boundaries from evidence
```

A more "agentic" implementation is not automatically better. A more deterministic implementation is
not automatically better either if it cannot deliver useful user-facing behavior. The target is the
smallest control plane that reliably turns authoritative observations into correct, truthful actions
and responses at acceptable inference cost.

# v1.0 readiness

v1.0 remains the first formal/stable release. Before v1.0 require at least:

- public API cleanup;
- removal/deprecation completion for duplicate Harness/loop concepts;
- documented SemVer policy;
- stable `AgentDefinition` serialization/versioning;
- documented package boundaries;
- complete migration guidance;
- representative end-to-end examples;
- session concurrency/transaction review;
- crash/retry/idempotency tests;
- security review;
- provider/integration failure semantics;
- observability contract;
- benchmark evidence across multiple prospective subjects;
- production deployment guidance;
- generated API reference and compatibility matrix;
- proof that framework-specific types do not leak through core abstractions.
