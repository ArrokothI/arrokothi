# Agent SDK v0.4 Roadmap

This document is a future plan, not a description of v0.35 functionality. Each item requires a
separate design, threat model, and acceptance test before implementation.

## Skills

Define a provider-neutral, versioned `SkillDefinition` beginning with static/manual Skills:

- metadata plus instructions and referenced resources;
- explicit Phase Skill scoping;
- serialization and provenance rules;
- adapters for provider-specific Skill systems where semantics remain compatible;
- investigation of Strands-compatible Skill patterns;
- investigation of Claude `SKILL.md` interoperability.

Automatic permanent Skill learning must not be the default. A later hypothesis is:

```text
sessions / corrections / Working Notes
→ SkillProposal
→ offline evaluation
→ human approval
→ versioned Skill
```

The Planner must never silently rewrite its permanent capabilities.

## Subagents

Study isolated-context workers with:

- least-privilege capability scope;
- explicit input/evidence/result contracts;
- bounded budgets and cancellation propagation;
- parent-owned acceptance of results;
- durable trace semantics without exposing hidden reasoning;
- an evaluation of whether Strands subagent facilities fit under Agent_SDK abstractions.

Teams and general multi-agent orchestration remain separate, later questions.

## MCP

Use MCP, if adopted, as a Tool/Knowledge interoperability protocol. Agent_SDK must still own
`ToolExecutor`, `CapabilityGateway`, confirmation, idempotency, Phase scope, and ToolResult truth.
MCP descriptions and annotations are untrusted hints, never authorization.

## Preflight collapse experiment

Study whether the first inner-loop call can safely combine:

```text
state synchronization
+ Phase proposal
+ planning
+ potential direct answer or capability request
```

The target is a common direct-response path with one model call. Unresolved questions include:

- how proposed Memory is validated before later content in the same call depends on it;
- whether Flow transitions can change the capability catalog during that call;
- how to persist a truthful partial result if the call fails;
- how to separate user-established facts from inference;
- how deterministic skip/fallback behavior works;
- whether provider tool protocols can express the transaction cleanly.

No collapse should trade away authority, replayability, or inspectable call accounting.

## Long-term execution context

Investigate Strands resumable session/execution mechanisms. Define when a business agent should
start with fresh temporary context, when it may resume, what is persisted, how model history is
invalidated after authoritative state changes, and how migrations work across definition/model
versions. Agent_SDK Durable Session remains the default truth source.

## Working Notes, Long-Term Memory, and Skills

- **Working Notes:** ephemeral semantic interpretations that help the current/recent task and may
  expire.
- **Long-Term Memory:** durable, schema-governed user/application facts with provenance and explicit
  update authority.
- **Skills:** versioned reusable capability/instruction bundles installed through a governed
  lifecycle.

These concepts must not be merged into an undifferentiated model transcript.

## Rule and instruction refinement

Continue planner/response/both instruction scopes. Consider optional semantic response validation
only for requirements that cannot be enforced deterministically. Prefer schemas, Gateway checks,
typed executors, and state machines over a general LLM judge whenever possible.

## Flow evolution

Keep Flow as coarse Phase and capability scope. Evaluate richer Flow compilation to Strands Graph or
Workflow only when concrete use cases demonstrate value. Do not assume graph orchestration is
necessary for ordinary agent loops.

## Host integration

Design, but do not yet ship:

- a browser/client SDK;
- a production Host Context endpoint;
- authenticated-backend trust and identity rules;
- optional proactive external-event triggers with explicit consent and rate limits.

Host observations must remain distinct from automatic agent invocation.

## v1.0 readiness

**v1.0 is the first formal/stable release.** Before v1.0, require:

- public API cleanup;
- removal/deprecation completion for duplicate Harness/loop concepts;
- a documented SemVer policy;
- stable `AgentDefinition` serialization and versioning;
- documented package boundaries;
- a complete migration guide;
- end-to-end commercial examples;
- session concurrency and transaction review;
- crash/retry/idempotency tests;
- security review;
- provider/integration failure semantics;
- an observability contract;
- formal P01/P02/P03/P04 benchmark evidence;
- production deployment guidance;
- generated API reference;
- a compatibility matrix;
- proof that no framework-specific type leaks through core.
