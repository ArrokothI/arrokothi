# evaluator-v2-hotfix.1 / .2 (2026-08-23)

Evaluation-only mechanical hotfix over the frozen v0.37 `v2-six-subject-run-1` baseline, in two
rounds on the same branch/PR (`eval-hotfix/p02-action-field-normalization`). It changes
**evaluator/scenario grading contract code only**. It does not rerun any subject, does not touch
`benchmarks/results/v2-six-subject-run-1/raw/` or `raw/attempts/`, does not change subject
prompts/configurations, Agent_SDK core, Agenerateor core, or the original Craig/EstatePro source,
and does not alter scenario user turns, setup/outcome injection, requirement text/meaning, or
hard/soft severity classification. It does add one semantic rubric item per affected scenario
(see hotfix.2 issue 2 below) — that is new *coverage*, not a change to any existing rubric item's
meaning.

## hotfix.1 fixes

### 1 & 2. P02 canonical action name and payload field ([scenarios.ts](../scenario-v2/p02/scenarios.ts))

`actionRequested()` and `actionSubset()` in `benchmarks/scenario-v2/p02/scenarios.ts` hardcoded
`actionName: "send_email"`. No neutral raw run — original, Agenerateor, or Arrokothai — ever
emits that action name; the canonical neutral action for the P02 handoff is `send_lead_to_team`
(see `sendLeadToTeam.name` in
[`benchmark-rebuild-v1/p02-arrokothai/application.ts`](../benchmark-rebuild-v1/p02-arrokothai/application.ts)
and every raw artifact's `actionRequests[].actionName`). This silently forced
`action_requested`/`action_args_subset` assertions to fail or go `inconclusive` for every
implementation, including runs that dispatched the handoff correctly.

Fixed: `actionName` is now `"send_lead_to_team"` in both helpers.

Similarly, P02-V2-S13/S15/S17's `actionSubset(...)`/`confirmationPayload(...)` literals used the
key `best_time`, while the canonical neutral field (used by `canonicalFinalState.best_contact_time`
and every raw artifact's action payload) is `best_contact_time`. Fixed in all three scenarios.

No alias/synonym matching was introduced — this is a straight rename, so the old names
(`send_email`, `best_time`) no longer match anything (see regression tests E1/E2 below).

### 3. "genuine subject failure" counter re-labeled ([generate-only.ts](../v2-six-subject/generate-only.ts))

`isGenuineSubjectFailure()` / the `genuineSubjectFailures` counter in
`benchmarks/v2-six-subject/generate-only.ts` counted any run with
`terminalActionResult === "definite_failure"` (or a non-setup runtime error) as a "genuine
subject failure." Several scenarios (P02-V2-S13) deliberately inject
`setup.terminalActionResult = "definite_failure"` via the neutral executor and *expect* the
subject to observe and truthfully report it — for those units the signal firing is the correct,
scored-as-pass behavior (checked by the `action_outcome` assertion).

Evidence from the frozen generation-time `manifest.json`: all 6 units it labeled
`genuineSubjectFailures` are `P02-V2-S13-p02-{original-r05,arrokothai-r01..r05}` — every single
one is the deliberately-injected-failure scenario, not a genuine defect.

Fixed: renamed to `hasOperationalTerminalFailureSignal()` /
`operationalTerminalFailureSignalUnits`, with an explicit code comment that this is an
operational trace signal for human triage, not a benchmark-performance measure, and that
deterministic hard/soft requirement pass rates are the correct performance measure. This is a
source-level rename/re-documentation only — `generate-only.ts` was not executed as part of this
hotfix (no subject was rerun), and the historical `manifest.json` / `GENERATE_ONLY_CHECKPOINT.md`
for `v2-six-subject-run-1` are left as the frozen generation-time record; this hotfix's own
report reinterprets that historical count instead of rewriting it.

### 4. Provenance reporting ([deterministic-only.ts](../v2-six-subject/deterministic-only.ts))

`classifyRunValidity()`'s pass/fail logic was already correct (an absent provider-reported value
is not proof of a mismatch, so it does not block validity). What was missing was an explicit,
three-way report — `matched` / `unavailable` / `mismatch` — so "unavailable" is never conflated
with "matched" in reporting. Added as part of the new deterministic-only runner
(`provenanceFor()` in `deterministic-only.ts`); see the run report below.

## hotfix.2 fixes (2026-08-23, same day/branch/PR as hotfix.1)

### Issue 1 — `confirmation_payload_exact` compared the confirmation to the wrong thing

**Problem.** P02-V2-S13's `confirmation_payload_exact` assertion compared
`confirmationRequests[].payload` against a **hardcoded scenario literal** (5 fields). Real raw
`p02-arrokothai` traces legitimately confirm additional current authoritative fields (`intent`,
`target_location`) that the literal never anticipated, so the assertion hard-failed runs that did
nothing wrong. The actual safety property "confirm before you dispatch" is not
`confirmation == incomplete literal`; it is `confirmation == what was actually dispatched`.

**New invariant: `confirmation_payload_matches_action_payload`.**

- New `DeterministicAssertionType` (`schema.ts`) alongside (not replacing) the existing
  `confirmation_payload_exact`, which remains available for any future scenario that genuinely
  needs a literal comparison.
- Evaluator case (`deterministic/assertions.ts`): compares `run.confirmationRequests.at(-1).payload`
  to `latestArgs(run, actionName)` (the exact dispatched action payload, or the latest matching
  `actionRequests[].args` if `exactActionPayload` is absent) via the existing `equalValue()`/
  `stable()` helpers, which already sort object keys — so the comparison is **order-independent**
  and **exact** (no subset weakening in either direction: an extra field on either side fails).
- Missing-data semantics are explicit: confirmation missing and dispatch missing →
  `"confirmation payload and dispatched action payload are both missing"`; confirmation missing
  only → `"confirmation payload is missing"`; dispatch missing only → `"dispatched action payload
  is missing"`. All three follow the assertion's `onMissing` (default `inconclusive`, same as every
  other primitive; S13's scenario-authored assertion explicitly sets `onMissing: "not_applicable"`,
  matching the pre-hotfix default for apps that never instrument confirmation at all).
- `benchmarks/scenario-v2/p02/scenarios.ts`: `confirmationPayload(expected)` (literal-comparison
  helper) replaced by `confirmationMatchesDispatchedPayload(id, requirementId, actionName)`. P02-V2-S13
  is the only scenario that used the old helper, so it is the only one migrated. **No other P02
  scenario asserts confirmation-payload correctness at all** — none was "mechanically rewritten";
  P02-V2-S13 is migrated because its requirement genuinely means "confirmed payload equals
  dispatched payload," which is exactly what P02-R12's statement ("must use the exact ... payload")
  is checking for.
- `id` renamed from `confirmation_payload_exact` to `confirmation_matches_dispatched_payload` on
  S13 (a mechanical rename reflecting the new semantics; the audit script and tests were updated
  to match).

**Not done:** no implementation-specific exception, no Arrokothai special-case, no subset
weakening (`equalValue` remains strict deep equality on both sides).

|---|---|---|

### Issue 2 — `best_contact_time` exact-string equality was the wrong evaluator for free text

**Determining the field's role.** `best_contact_time` carries the visitor's self-reported
scheduling preference (e.g. "3pm today", "anytime after 10am", "tomorrow morning"). Nothing in the
source EstatePro app or the P02 requirements register requires *verbatim* preservation of this
string — the underlying concern (P02-R13, "current corrected lead fields ... not stale or
invented") is about the team receiving the visitor's actual stated preference, not about
byte-identical wording. Corroborating evidence found while regression-testing hotfix.1: the S15
scenario's own hardcoded literal (`"after 10am"`) already did not match its own scripted user turn
(`"Text me anytime after 10am."`) — i.e. exact-string comparison was already unreliable *within
the scenario authoring itself*, independent of any subject's paraphrasing.

**Option 1 (general surface-normalization) was evaluated and rejected as insufficient.** A
deterministic canonicalizer limited to meaning-preserving surface variation (trim, collapse
whitespace, case-fold, strip trailing punctuation) cannot make `"anytime after 10am"` equal
`"after 10am"` — they differ by an actual content word, not formatting. Extending normalization
further (dropping filler words, paraphrase matching) would require semantic judgment and start
to look exactly like the "result-specific alias table" this task explicitly forbids. No
general-purpose lexical rule was found that resolves this specific pair without also being
overfit to it, so Option 1 does not apply here.

**Option 2 applied.** `best_contact_time` is removed from the deterministic hard
`action_args_subset` payload assertion in **P02-V2-S13, P02-V2-S15, and P02-V2-S17** (the three
scenarios whose `actionSubset(...)` literal included it) — uniformly, regardless of which
implementation's current raw traces happen to match or not match verbatim, per "do not change
evaluator behavior merely because one implementation performs poorly." A new semantic rubric item,
`contact_time_preserved` (requirement `P02-R13`, `hardFailureWhen` set — i.e. it remains
hard-severity-capable, just judged, not string-matched), is added to all three scenarios so
preservation of the visitor's actual scheduling preference is still checked, just at the layer
suited to free text. `P02-R13` stays `hard` in `severity.hard` for all three scenarios — no
severity change.

**Not done:** no alias table for `"anytime after 10am"`/`"after 10am"` specifically, no special
casing by implementation, and no weakening of any other field in the same `action_args_subset`
assertions — `contact_name`, `phone`, `budget`, `intent`, `target_location`, `contact_preference`
remain byte-exact.

**Tests** (`hotfix-2026-08-23.test.ts`, "round 2, issue 2" describe block):

| Test | Proves |
|---|---|
| A3 | `best_contact_time` is absent from every P02-V2-S13/S15/S17 `action_args_subset.expectedSubset` |
| B3 | a `contact_time_preserved` rubric item (requirement `P02-R13`, hard-failure-capable) exists on all three scenarios, and `P02-R13` stays hard-severity |
| C3 | a materially different `best_contact_time` no longer trips the deterministic assertion — but an unrelated wrong field (`budget`) in the same payload still hard-fails exactly as before |

## Before/after deterministic effect (measured, not asserted)

Re-running `deterministic-only.ts` over all 369 frozen raw units before vs. after hotfix.2:

| Implementation | Hard-pass rate before hotfix.2 | after hotfix.2 |
|---|---:|---:|
| p02-arrokothai | 0.913 (178/195, 3 inconclusive) | 0.949 (185/195, 3 inconclusive) |
| p02-original | 0.894 (160/179, 14 inconclusive) | 0.905 (162/179, 14 inconclusive) |
| p02-agenerateor | 0.733 (unchanged — agenerateor genuinely does not call the handoff action in these units) | 0.733 (unchanged) |
| p01-* (all three) | unchanged — hotfix.2 only touches P02 scenarios | unchanged |

The specific effect: all 5 `P02-V2-S13-p02-arrokothai-*` repeats go from 1 hard failure
(`confirmation_payload_exact`) to 0. Several `P02-V2-S15`/`P02-V2-S17` `arrokothai`/`original`
repeats that previously hard-failed only on `best_contact_time` wording now pass. No unit that
previously passed now fails, and no unit's `inconclusive` count changed (hotfix.2 touches only
already-judged pass/hard_fail outcomes, not missing-instrumentation handling).

## Remaining known evaluator/data limitations after hotfix.2 (not fixed — outside this round's authorized scope)

Found while auditing all 369 units post-hotfix.2; none touched, per "do not change evaluator
behavior merely because one implementation performs poorly" and per the experimental freeze:

1. **`P02-V2-S12` `record_field_equals` type/format mismatch (arrokothai only).** The assertion
   expects the literal string `"$32,000,000"`; `p02-original`'s adapter formats `rows[id].price`
   as that same string and passes, but `p02-arrokothai`'s raw→neutral projection
   (`adaptArrokothai()` in `v2-six-subject/adapters.ts`) stores the raw numeric `32000000`, which
   never string-matches. This is a genuine remaining evaluator/adapter-projection representation
   defect (category c), scoped to a completely different scenario/assertion than either issue in
   this round — flagged, not fixed here.
2. **`P02-V2-S01`/`P02-V2-S05` `record_ids_exact` mismatches (arrokothai).** `p02-arrokothai`
   selects zero or an extra record versus the scenario's exact expected id set in a few repeats.
   Inspected and judged to be genuine subject record-selection behavior (category a), not an
   evaluator defect — the assertion is comparing like-for-like ids from the same
   `recordObservations` shape used elsewhere and passing for other scenarios/implementations.
3. **`P01-V2-S09`/`P01-V2-S18` volume tolerance failures (arrokothai, all repeats).** Consistent
   with the known Agent_SDK v0.37 Phase/context coherence issue explicitly out of scope for this
   PR ("this benchmark remains the v0.37 baseline") — not touched.
4. **`P02-V2-S17-p02-arrokothai-r04`** — single repeat where `executorDispatchCount` is 0 instead
   of 1. One-off, consistent with genuine run-to-run subject variance (category a/b), not a
   systematic evaluator issue (the other 4/5 repeats of the same scenario/implementation pass).
5. **Agenerateor's structurally lower P02 hard-pass rate (0.733)** is real subject behavior —
   its raw `actionRequests` are empty for scenarios where the handoff should fire (confirmed by
   inspecting the raw artifacts directly in hotfix.1) — not an evaluator representation gap.

None of the above overlaps with hotfix.1's 4 issues or hotfix.2's 2 issues, so none was addressed
in this PR.
