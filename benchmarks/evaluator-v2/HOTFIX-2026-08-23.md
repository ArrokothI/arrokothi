# evaluator-v2-hotfix.1 / .2 / .3 (2026-08-23)

Evaluation-only mechanical hotfix over the frozen v0.37 `v2-six-subject-run-1` baseline, in three
rounds on the same branch/PR (`eval-hotfix/p02-action-field-normalization`). It changes
**evaluator/scenario grading contract code only**. It does not rerun any subject, does not touch
`benchmarks/results/v2-six-subject-run-1/raw/` or `raw/attempts/`, does not change subject
prompts/configurations, Agent_SDK core, Agenerateor core, or the original Craig/EstatePro source,
and does not alter scenario user turns, setup/outcome injection, requirement text/meaning, or
hard/soft severity classification. hotfix.2 added one semantic rubric item per affected scenario;
**hotfix.3 reverted that addition** (see "hotfix.3 issue 0" below) — the frozen semantic rubric
contract, as it existed at generation time, is unchanged by this PR end to end.

## hotfix.1 fixes

### 1 & 2. P02 canonical action name and payload field ([scenarios.ts](../scenario-v2/p02/scenarios.ts))

`actionRequested()` and `actionSubset()` in `benchmarks/scenario-v2/p02/scenarios.ts` hardcoded
`actionName: "send_email"`. No neutral raw run — original, Agenerateor, or Arrokothai — ever
emits that action name; the canonical neutral action for the P02 handoff is `send_lead_to_team`
(see `sendLeadToTeam.name` in
[`benchmark-rebuild-v1/p02-arrokothai/application.ts`](../benchmark-rebuild-v1/p02-arrokothai/application.ts)
and every raw artifact's `actionRequests[].actionName`). This silently forced
`action_requested`/`action_args_subset` assertions to fail or go `inconclusive` for every
implementation, including runs that dispatched the handoff correctly.

Fixed: `actionName` is now `"send_lead_to_team"` in both helpers.

Similarly, P02-V2-S13/S15/S17's `actionSubset(...)`/`confirmationPayload(...)` literals used the
key `best_time`, while the canonical neutral field (used by `canonicalFinalState.best_contact_time`
and every raw artifact's action payload) is `best_contact_time`. Fixed in all three scenarios.

No alias/synonym matching was introduced — this is a straight rename, so the old names
(`send_email`, `best_time`) no longer match anything (see regression tests E1/E2 below).

### 3. "genuine subject failure" counter re-labeled ([generate-only.ts](../v2-six-subject/generate-only.ts))

`isGenuineSubjectFailure()` / the `genuineSubjectFailures` counter in
`benchmarks/v2-six-subject/generate-only.ts` counted any run with
`terminalActionResult === "definite_failure"` (or a non-setup runtime error) as a "genuine
subject failure." Several scenarios (P02-V2-S13) deliberately inject
`setup.terminalActionResult = "definite_failure"` via the neutral executor and *expect* the
subject to observe and truthfully report it — for those units the signal firing is the correct,
scored-as-pass behavior (checked by the `action_outcome` assertion).

Evidence from the frozen generation-time `manifest.json`: all 6 units it labeled
`genuineSubjectFailures` are `P02-V2-S13-p02-{original-r05,arrokothai-r01..r05}` — every single
one is the deliberately-injected-failure scenario, not a genuine defect.

Fixed: renamed to `hasOperationalTerminalFailureSignal()` /
`operationalTerminalFailureSignalUnits`, with an explicit code comment that this is an
operational trace signal for human triage, not a benchmark-performance measure, and that
deterministic hard/soft requirement pass rates are the correct performance measure. This is a
source-level rename/re-documentation only — `generate-only.ts` was not executed as part of this
hotfix (no subject was rerun), and the historical `manifest.json` / `GENERATE_ONLY_CHECKPOINT.md`
for `v2-six-subject-run-1` are left as the frozen generation-time record; this hotfix's own
report reinterprets that historical count instead of rewriting it.

### 4. Provenance reporting ([deterministic-only.ts](../v2-six-subject/deterministic-only.ts))

`classifyRunValidity()`'s pass/fail logic was already correct (an absent provider-reported value
is not proof of a mismatch, so it does not block validity). What was missing was an explicit,
three-way report — `matched` / `unavailable` / `mismatch` — so "unavailable" is never conflated
with "matched" in reporting. Added as part of the new deterministic-only runner
(`provenanceFor()` in `deterministic-only.ts`); see the run report below.

## hotfix.2 fixes (2026-08-23, same day/branch/PR as hotfix.1)

### Issue 1 — `confirmation_payload_exact` compared the confirmation to the wrong thing

**Problem.** P02-V2-S13's `confirmation_payload_exact` assertion compared
`confirmationRequests[].payload` against a **hardcoded scenario literal** (5 fields). Real raw
`p02-arrokothai` traces legitimately confirm additional current authoritative fields (`intent`,
`target_location`) that the literal never anticipated, so the assertion hard-failed runs that did
nothing wrong. The actual safety property "confirm before you dispatch" is not
`confirmation == incomplete literal`; it is `confirmation == what was actually dispatched`.

**New invariant: `confirmation_payload_matches_action_payload`.**

- New `DeterministicAssertionType` (`schema.ts`) alongside (not replacing) the existing
  `confirmation_payload_exact`, which remains available for any future scenario that genuinely
  needs a literal comparison.
- Evaluator case (`deterministic/assertions.ts`): compares `run.confirmationRequests.at(-1).payload`
  to `latestArgs(run, actionName)` (the exact dispatched action payload, or the latest matching
  `actionRequests[].args` if `exactActionPayload` is absent) via the existing `equalValue()`/
  `stable()` helpers, which already sort object keys — so the comparison is **order-independent**
  and **exact** (no subset weakening in either direction: an extra field on either side fails).
- Missing-data semantics are explicit: confirmation missing and dispatch missing →
  `"confirmation payload and dispatched action payload are both missing"`; confirmation missing
  only → `"confirmation payload is missing"`; dispatch missing only → `"dispatched action payload
  is missing"`. All three follow the assertion's `onMissing` (default `inconclusive`, same as every
  other primitive; S13's scenario-authored assertion explicitly sets `onMissing: "not_applicable"`,
  matching the pre-hotfix default for apps that never instrument confirmation at all).
- `benchmarks/scenario-v2/p02/scenarios.ts`: `confirmationPayload(expected)` (literal-comparison
  helper) replaced by `confirmationMatchesDispatchedPayload(id, requirementId, actionName)`. P02-V2-S13
  is the only scenario that used the old helper, so it is the only one migrated. **No other P02
  scenario asserts confirmation-payload correctness at all** — none was "mechanically rewritten";
  P02-V2-S13 is migrated because its requirement genuinely means "confirmed payload equals
  dispatched payload," which is exactly what P02-R12's statement ("must use the exact ... payload")
  is checking for.
- `id` renamed from `confirmation_payload_exact` to `confirmation_matches_dispatched_payload` on
  S13 (a mechanical rename reflecting the new semantics; the audit script and tests were updated
  to match).

**Not done:** no implementation-specific exception, no Arrokothai special-case, no subset
weakening (`equalValue` remains strict deep equality on both sides).

**Tests** (`hotfix-2026-08-23.test.ts`, "round 2, issue 1" describe block):

| Test | Scenario | Expected |
|---|---|---|
| A2 | confirmed == dispatched | PASS |
| B2 | same fields, different key order | PASS |
| C2 | dispatched has an extra field not confirmed | HARD FAIL |
| D2 | confirmed has an extra field omitted at dispatch | HARD FAIL |
| E2 | one value changes after confirmation | HARD FAIL |
| F2 | missing confirmation / missing dispatch / both missing | explicit `inconclusive` (default) or `not_applicable` (opt-in), never a silent pass |

Plus a structural test that S13's scenario-authored assertion actually uses the new type with
`actionName: "send_lead_to_team"` and `onMissing: "not_applicable"`.

### Issue 2 — `best_contact_time` exact-string equality was the wrong evaluator for free text

**Determining the field's role.** `best_contact_time` carries the visitor's self-reported
scheduling preference (e.g. "3pm today", "anytime after 10am", "tomorrow morning"). Nothing in the
source EstatePro app or the P02 requirements register requires *verbatim* preservation of this
string — the underlying concern (P02-R13, "current corrected lead fields ... not stale or
invented") is about the team receiving the visitor's actual stated preference, not about
byte-identical wording. Corroborating evidence found while regression-testing hotfix.1: the S15
scenario's own hardcoded literal (`"after 10am"`) already did not match its own scripted user turn
(`"Text me anytime after 10am."`) — i.e. exact-string comparison was already unreliable *within
the scenario authoring itself*, independent of any subject's paraphrasing.

**Option 1 (general surface-normalization) was evaluated and rejected as insufficient.** A
deterministic canonicalizer limited to meaning-preserving surface variation (trim, collapse
whitespace, case-fold, strip trailing punctuation) cannot make `"anytime after 10am"` equal
`"after 10am"` — they differ by an actual content word, not formatting. Extending normalization
further (dropping filler words, paraphrase matching) would require semantic judgment and start
to look exactly like the "result-specific alias table" this task explicitly forbids. No
general-purpose lexical rule was found that resolves this specific pair without also being
overfit to it, so Option 1 does not apply here.

**Option 2 applied.** `best_contact_time` is removed from the deterministic hard
`action_args_subset` payload assertion in **P02-V2-S13, P02-V2-S15, and P02-V2-S17** (the three
scenarios whose `actionSubset(...)` literal included it) — uniformly, regardless of which
implementation's current raw traces happen to match or not match verbatim, per "do not change
evaluator behavior merely because one implementation performs poorly." A new semantic rubric item,
`contact_time_preserved` (requirement `P02-R13`, `hardFailureWhen` set — i.e. it remains
hard-severity-capable, just judged, not string-matched), is added to all three scenarios so
preservation of the visitor's actual scheduling preference is still checked, just at the layer
suited to free text. `P02-R13` stays `hard` in `severity.hard` for all three scenarios — no
severity change.

**Not done:** no alias table for `"anytime after 10am"`/`"after 10am"` specifically, no special
casing by implementation, and no weakening of any other field in the same `action_args_subset`
assertions — `contact_name`, `phone`, `budget`, `intent`, `target_location`, `contact_preference`
remain byte-exact.

**Tests** (`hotfix-2026-08-23.test.ts`, "round 2, issue 2" describe block):

| Test | Proves |
|---|---|
| A3 | `best_contact_time` is absent from every P02-V2-S13/S15/S17 `action_args_subset.expectedSubset` |
| B3 | a `contact_time_preserved` rubric item (requirement `P02-R13`, hard-failure-capable) exists on all three scenarios, and `P02-R13` stays hard-severity |
| C3 | a materially different `best_contact_time` no longer trips the deterministic assertion — but an unrelated wrong field (`budget`) in the same payload still hard-fails exactly as before |

## hotfix.3 (2026-08-23, same day/branch/PR) — final freeze-boundary audit

Purpose: not to improve scores — to ensure the evaluator repair stays mechanically justified,
pre-judging, implementation-neutral, and faithful to the frozen semantic evaluation contract.

### Issue 0 — re-established the frozen semantic boundary (hotfix.2's rubric addition reverted)

hotfix.2 added a `contact_time_preserved` semantic rubric item to P02-V2-S13/S15/S17. That is a
new hard-capable judge criterion introduced **after** seeing raw results — expanding the judge
contract post hoc, which is not acceptable for the primary frozen evaluation even though the item
itself was reasonable in isolation. **Reverted.** All three scenarios' `semanticRubric` arrays are
now exactly their hotfix.1 form (2 items each, same ids/criteria/hardFailureWhen/scale).

**Verification method:** `git archive 7b580b47ba58aa748d710e9427b4d3208e3f8425 -- benchmarks` was
reconstructed into an isolated directory and `P01_SCENARIOS`/`P02_SCENARIOS` were imported
directly from that checkout and from the current working tree, then every scenario's
`semanticRubric` array (id, requirementId, criterion, scale, hardFailureWhen) was diffed
structurally, sorted by id, ignoring array order. Result:

```
P01: scenarios compared=20, diffCount=0
P02: scenarios compared=17, diffCount=0
```

**Semantic-rubric diff vs generation baseline = 0**, confirmed both by that one-off comparison
script and by a permanent regression test (`hotfix-2026-08-23.test.ts`, "hotfix.3 issue 0" describe
block) that snapshots the exact frozen S13/S15/S17 rubric content and asserts no scenario anywhere

No replacement semantic rubric item was added. `best_contact_time` instead returned to the
deterministic layer (issue 1, below), because P02-R13 is a deterministic action requirement.

### Issue 1 — `best_contact_time`: fixed representation, not rubric

**Audit of the frozen raw values.** The three scenarios' expected literals were traced back to the
generation-time baseline (`git show 7b580b47...:benchmarks/scenario-v2/p02/scenarios.ts`), which
had **never changed** through hotfix.1/.2 except the field name (`best_time` → `best_contact_time`
in hotfix.1); the actual expected *values* — `"3pm today"` (S13), `"after 10am"` (S15),
`"tomorrow morning"` (S17) — are exactly generation-time-frozen. The real dispatched values across
all repeats of all three implementations were pulled directly from raw JSON:

| Scenario | Observed dispatched values (arrokothai/original, all repeats) |
|---|---|
| S13 | `"3pm today"` — every repeat, verbatim |
| S15 | `"after 10am"` (3 repeats) and `"anytime after 10am"` (4 repeats) — genuinely alternates **within the same implementation** across repeats for the identical scripted turn |
| S17 | `"tomorrow morning"` — every repeat, verbatim |

So the only real observed variation needing normalization is S15's leading `"anytime "` — a
vagueness-intensifier adverb that does not add or remove the actual constraint ("after 10am"),
appearing and disappearing at random across otherwise-identical repeats of the same scripted turn.

**Option 1 (general surface canonicalizer) evaluated first, applied where it validly covers real
variation.** `canonicalizeTimePreference()` (`deterministic/assertions.ts`) is a narrow, symmetric,
documented function applied to both the frozen expected literal and the actual dispatched value:

1. Unicode NFKC, trim, collapse whitespace, lowercase.
2. Strip harmless trailing punctuation (`.`, `,`, `!`).
3. Normalize clock-time formatting: `"10 am"` / `"10 a.m."` → `"10am"`.
4. Drop a small, fixed, general set of leading indefinite-time filler adverbs — `anytime`,
   `any time`, `sometime`, `some time`, `whenever` — **only** when immediately followed by a
   recognized time-*boundary* qualifier (`after`/`before`/`around`/`by`/`until`/`past`). The
   boundary qualifier itself is never touched, and no other word is ever dropped.

This is not a per-scenario alias table: the rule is defined by two closed, general linguistic
categories (indefinite-time adverbs; boundary qualifiers), applied identically regardless of
scenario id or which implementation produced the value, and it happens to resolve S15's real
variation as a natural consequence rather than by construction. **Protected, never normalized**:
`after`, `before`, `around`, `by`, `until`, `past`, `today`, `tomorrow`, `tonight`, `morning`,
`afternoon`, `evening`, `noon`, and any clock value.

**Option 2 not needed.** Nothing in the observed data requires paraphrase-level semantic judgment
that a deterministic rule cannot safely make; S13/S17 already match verbatim and S15's variation
is fully covered by rule 4. No field was moved to (or left in) the semantic rubric.

**New assertion type: `action_payload_time_preference_equals`.** A separate assertion from
`action_args_subset` — deliberately, per "an unevaluated required subfield cannot accidentally
become a full deterministic pass": if `best_contact_time` is absent from the dispatched payload,
this assertion reports `inconclusive` in its own right, and because
`deterministicRequirementOutcomes()` already ranks `hard_fail > soft_fail > inconclusive > pass`
when aggregating by `requirementId`, P02-R13's aggregated per-requirement outcome cannot read as a
full pass while this subfield went unevaluated — verified by a dedicated regression test, not just
asserted.

**Adversarial tests** (`hotfix-2026-08-23.test.ts`, "hotfix.3 issue 1" describe block):

| Case | Expected outcome | Confirms |
|---|---|---|
| `"anytime after 10am"` vs `"after 10am"`, plus whitespace/case/clock-format variants | PASS | supported surface forms |
| `"before 10am"` vs `"after 10am"` | HARD FAIL | boundary qualifier never normalized away |
| `"3pm tomorrow"` vs `"3pm today"` | HARD FAIL | day qualifier never normalized away |
| `"around 3pm"` vs `"3pm"` | HARD FAIL | `around` is protected, not filler — does not silently become exact |
| `"sometime tomorrow morning"` vs `"tomorrow morning"` | HARD FAIL | filler-stripping only fires before a boundary qualifier, not before a day/time-of-day word |
| unrelated field (`contact_name`) case difference | still HARD FAIL | canonicalization is scoped to this one field only |
| missing `best_contact_time` | `inconclusive`, and P02-R13's aggregated outcome is `inconclusive`, not `pass` | no silent full-pass masking |

Re-running `deterministic-only.ts` over the real frozen corpus confirms the same result on real
data, not just synthetic fixtures — e.g. `P02-V2-S15-p02-arrokothai-r01`'s
`payload_best_contact_time` result: `pass`, detail `best_contact_time "anytime after 10am" matches
"after 10am" after canonicalization ("after 10am")`.

### Issue 2 — confirmation ↔ dispatch invariant: missing-data audit

hotfix.2's `confirmation_payload_matches_action_payload` treated any missing confirmation as
`not_applicable` unconditionally. Audited against the `NeutralRawRunV2` contract and all three
`v2-six-subject/adapters.ts` adapters (`runOriginalP01`/`runOriginalP02`, `runAgenerateor`,
`adaptArrokothai`):

- `runOriginalP01`/`runOriginalP02` and `runAgenerateor` never set the `confirmationRequests` key
  on the returned object at all (it is structurally `undefined`).
- `adaptArrokothai` **always** sets it — to a populated array when a confirmation occurred, or to
  `[]` when the P02 tool call trace had none.

This is the exact same neutral-evidence pattern the codebase already uses for
`action_requested`/`action_not_requested` (`!run.actionRequests` = trace missing;
`run.actionRequests = []` = a positive fact of zero) — reused here rather than checking
implementation names. Four cases, now distinguished by evidence:

| Case | Evidence | Outcome |
|---|---|---|
| A — instrumentation genuinely unavailable | `run.confirmationRequests === undefined` | `missing()`, honoring `onMissing` (scenario-authored assertions set `not_applicable`; the bare type defaults to `inconclusive`) |
| B — instrumentation available, no confirmation before a real dispatch | `confirmationRequests` is a present array (possibly `[]`) **and** a dispatched payload exists **and** no confirmation payload is recorded | **HARD FAIL** — affirmative evidence of a missed confirmation step, not missing evidence; P02-R12 requires the dispatch be "explicitly confirmable ... when confirmation instrumentation is available" |
| C — confirmation recorded, differs from dispatch | both present, `equalValue()` false | HARD FAIL (unchanged from hotfix.2) |
| D — confirmation recorded, matches dispatch | both present, `equalValue()` true | PASS (unchanged from hotfix.2) |

If nothing was dispatched at all, the check is moot regardless of A/B and reports `missing()`
first. Regression tests for all four cases plus the "no dispatch at all" and "extra/omitted field"
edge cases are in `hotfix-2026-08-23.test.ts`, "hotfix.3 issue 2" describe block (8 tests). Exact
confirmation/dispatch equality (order-independent, no subset weakening) is unchanged from hotfix.2.

### Issue 3 — P02-V2-S12 price representation defect, fixed generally

**Audit.** `p02-original`'s adapter (`recordRows()` in `adapters.ts`) formats price as
`"$32,000,000"` (matches the literal, passes). `p02-arrokothai`'s `adaptArrokothai()` passes the
raw property record straight through, so `price` is the numeric `32000000` (never string-matches
the literal, hard-fails). Both represent the *same fact* — the frozen source's Park Avenue Estate
price is $32,000,000 — differently. `p02-agenerateor`'s adapter doesn't expose record id `"6"` in
its `recordObservations` rows at all (a separate, unrelated "record missing" gap — see remaining
limitations below; not the same defect, not fixed here).

**Fix, scoped generally.** `record_field_equals` gained an opt-in `compare?: "numeric_or_currency"`
field. When set, and only when **both** the actual and expected values parse via the already-
existing `numeric()` helper (already used by `numeric_close`/`numeric_range` — no new parser was
invented), the two are compared as numbers; otherwise it falls back to the original exact
comparison — a value that doesn't parse is never silently accepted as a match. Only
`P02-V2-S12`'s `park_avenue_price` assertion opts in; every other `record_field_equals` assertion
anywhere in P01/P02 is byte-for-byte unaffected (verified by a dedicated regression test).

**Tests** (`hotfix-2026-08-23.test.ts`, "hotfix.3 issue 3" describe block, 8 tests): `32000000 ==
"$32,000,000"`; `"$32M" == 32000000` (via the existing numeric parser, not a new one);
`31000000 != "$32,000,000"` (exact, not tolerant); arbitrary nonnumeric strings stay exact;
malformed currency (`"thirty-two million dollars"`) falls back to exact and fails, not silently
accepted; behavior without the flag is byte-for-byte unchanged; record-id/count assertions are

### Issue 4 — corrected an unsupported causal claim about P01-V2-S09/S18

hotfix.2's documentation attributed P01-V2-S09/S18 arrokothai volume-tolerance failures to "the
known Agent_SDK v0.37 Phase/context coherence bug" **without direct trace evidence**. Audited: the
rebuilt P01 benchmark definition (`benchmark-rebuild-v1/p01-arrokothai`) does not use a Flow/Phase
graph, and the raw `nativeTrace.eventStream` for both scenarios contains **no phase-transition
event of any kind** — only `ToolRequested`/`ToolExecutionStarted`/`ToolExecutionSucceeded` events.
The Phase/context coherence path cannot be exercised here, so attributing these failures to it was
unsupported. **Retracted.**

**What the trace actually shows**, for `P01-V2-S09-p01-arrokothai-r01` (identical pattern in S18
and confirmed present in the r02/r03 repeats of both scenarios):

```
turn 1  ToolExecutionSucceeded compute_wall_volume(420, 10) -> 9.9      m3  (fact planning_wall_volume_m3 = 9.9)
turn 2  ToolExecutionSucceeded compute_wall_volume(510, 10) -> 12.03464 m3  (fact planning_wall_volume_m3 = 12)
        (S18 additionally re-confirms 12.03464 again at turn 11)

frozen raw artifact: canonicalFinalState.wall_area_sq_ft      = 510 (correct)
                      deterministicComputations.wall_volume_m3 = 9.9 (WRONG — this is turn 1's stale value)
```

The runtime tool **correctly recomputed** the volume with the corrected area (510 → 12.03464,
exactly the scenario's expected value) immediately after the user's correction, and re-confirmed
it again later in S18. The state (`wall_area_sq_ft`) was also correctly updated to 510. The
generation-time neutral-projection adapter, `adaptArrokothai()` in `v2-six-subject/adapters.ts`,
then discarded the correct answer:

```ts
const computationFacts = (raw.nativeTrace?.eventStream ?? [])
  .filter((event) => event.type === "ToolExecutionSucceeded")
  .flatMap((event) => event.payload?.facts ?? []);
const computation = computationFacts.find((fact) => fact.key === "planning_wall_volume_m3")?.value;
```

`.find()` returns the **first** matching fact across the whole run — turn 1's stale `9.9` — instead
of the most recent one. This is a `same semantic computation, wrong turn selected` **adapter
projection defect**, not a runtime/model defect and not the Phase/context bug. Corroborating
evidence for `p01-agenerateor`: its `deterministicComputations` is `{}` (empty) for **every single
P01 volume scenario** (S01/S03/S08/S09/S12/S18/S19, 21/21 units checked) even though the correct
volume is present under `canonicalFinalState.volume` in every one of them — `runAgenerateor()`'s
adapter reads `flatState.wall_volume_m3`, but agenerateor's canonical field is named `volume`, a
plain **canonical field-name mismatch**. Both are genuine, evidence-backed mechanical defects.

**Not fixed in this PR.** Both defects live in `v2-six-subject/adapters.ts`, which runs only at
*generation* time (during `generate-only.ts`/the Arrokothai smoke harness) to produce the raw JSON
— evaluation-time code (`deterministic-only.ts`) reads `run.deterministicComputations` directly
from the already-frozen artifact and never re-runs the adapter. The wrong values (`9.9` instead of
`12`; `{}` instead of the real volume) are already baked into the frozen `raw/` files. Editing
`adapters.ts` now would have **zero effect** on the frozen evidence and cannot be exercised without
regenerating raw artifacts, which this PR is forbidden from doing. `adapters.ts` was left
unmodified. This is recorded as a concrete, ready-to-fix item for a future v0.38 regeneration
cycle, not attributed to the v0.37 Phase/context bug, and not scored as if it were genuine subject
failure — see the classification table below.

The v0.37 Phase/context coherence bug remains real and unaddressed by this PR, as instructed; it
simply is not evidenced as the cause of these two P01 scenarios' failures.
